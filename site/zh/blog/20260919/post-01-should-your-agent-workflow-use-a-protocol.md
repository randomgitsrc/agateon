# 你的 agent 工作流到底该不该上协议？

现在的 agent 框架很多，大多数都要你先接受点什么：一个运行时、一个 SDK、一张图、一个托管服务。但在接受任何东西之前，有个更小也更难的问题值得先答：我的活到底需不需要一层编排？这个问题答错，两个方向都贵——流程太重，agent 的预算都花在写状态报告上；流程太轻，你会在最后才发现"做完了"的意思是"agent 不说话了"。

![封面：一张任务卡放在天平上；左盘是一条经过 3 道 gate 的短路径，右盘是经过 8 个 phase 的长路径。右侧一个青色算分节点读出三条证据，把天平压向短路径。标题是"你的 agent 工作流到底该不该上协议？"。](./images/cover.svg)

**TL;DR** —— 我们做了 Agateon，但"你该不该用它"的诚实答案是：不一定，而且这个决定不该靠感觉。先说三个词，下面全都绕着它们转：*gate* 是一个 phase 前进之前必须通过的一道检查；*ceremony*（仪式）是一个任务要走这套机器里的多少——thin、standard 还是 full；而 *fail-closed* 指的是：一道检查判不出来时，它倒向"拦住"而不是"放行"。agent 自己报的复杂度没有价值——只要听起来够勤勉，它会把一行修复说成"架构级改动"。所以仪式深度改成从 git 证据算出来：五个信号（文件类型、敏感路径、改动规模、反向引用影响面、领域标记）合成一个档位，再由一道 gate 朝一个方向检查这个声明——你永远可以要求比算分**更重**的仪式；而算分更高时申请走 thin 会被拦下。我们自己的数字，你可以拿去算账：一个任务的中位日历跨度约 21 小时、跨 13 个 commit，留下约 6700 行阶段产物。它买到的是 119 次 gate 运行，其中 3 次是真拦截——37 个任务里有 19 个带着至少一次派发重试。下面是算分机制、真实成本，以及什么时候你该跳过这一切去写个脚本。

## 靠感觉决定，会让你同时踩中两种失败

最直觉的做法是问 agent：这个任务复杂吗？没用，我们有证据：风险算分之所以存在，就是因为仪式深度以前靠自报，而自报的复杂度会朝着"agent 觉得你想听的方向"漂移。你问一个乐于助人的 agent 这个任务要不要走完整的八阶段，你会得到一个深思熟虑、自信、且毫无根据的"要"。

另一种失败是人这边的：因为改动"看起来很小"就跳过流程。我们自己写的任务 brief 就是证据。我核对 gate 加固那批的 brief 时，它引了 CI 兜底脚本的行号和一个证据文件计数；两个都错了——行号差了四行，计数差了五个。没人撒谎，也没人明显粗心，只是那些数字是被回忆出来的，而不是重新读出来的。这招一直管用，直到那个小改动碰了 auth 路径，或者修复落在了一个被另外十一个模块 import 的文件里。规模和风险是两根不同的轴，而凭记忆去估，第二根轴恰恰最容易估错。

## 算证据，不算自信

所以档位是算出来的。[`agate-risk-score.py`](https://github.com/randomgitsrc/agateon/blob/main/agate/scripts/agate-risk-score.py) 读暂存区的 diff，给五个信号打分，每个信号输出自己的证据行，而不是一个光秃秃的数字：

| 信号 | 读什么 | 什么情况算 high |
|---|---|---|
| file-type | 暂存路径 | 碰到协议本体或 gate 脚本 |
| sensitive-path | 路径关键词 | security、auth、permission、data-model |
| change-size | 暂存源文件数 | 超过五个 |
| impact | 反向引用 | 被改的模块在仓库别处被 import |
| domain-markers | P1 声明的领域 | 只做标注——不参与定档 |

合成规则故意做得无聊且二值：任一 high 就是 `full`；全 low 才是 `thin` 候选；其余是 `standard`。档位不由数值阈值决定，因为阈值会招来"阈值该定多少"的争论。下面是一个近期协议加固任务的逐字输出（算分时暂存区无改动；这个工具的文案本来就是中文，重点在数字）：

```text
risk_score: 6
tier: thin
file-type: low (无暂存改动)
sensitive-path: low (无暂存改动)
change-size: low (source files=0 <= 5)
impact: low (无反向引用)
domain-markers: [backend]
git_ok: true
```

注意最后一行。git 读不到时，工具不会悄悄返回一个友好的默认值——它报 `git_ok: false`，消费方把它当失败处理。算不出来的分说明不了任何风险，所以工具拒绝让它被读成低分。

![插图：五个证据信号（file-type、sensitive-path、change-size、impact、domain-markers）输入一个档位判定——thin、standard 或 full；此后声明可以要求比算分更重的仪式，要求更轻则会被拦，且 thin 路径仍然保留 P5 和 P6。底部横带对比成本（中位 21 小时、13 个 commit、约 6700 行产物）与它拦下了什么（119 次 gate 运行、3 次真拦截）。](./images/illustration-scoring.svg)

## 声明是单向的

算分只是一半机制。另一半是：声明要拿去和算分对照——而这里要讲清这个对照做到哪一步，包括它现在停在哪。你随时可以选**比算分更重**的仪式：一个算成 `thin` 的任务你声明 `full`，那是你的自由，代价只是时间。当算分是 `standard` 或 `full` 时申请走 **thin** 会被拦——一道 gate 把声明和算出来的档位比对，对不上就 exit 1，任务原地不动。**还没被强制的是中间那种情况**：算分 `full` 的任务声明 `standard`，今天能过路由检查，所以 `full` 分数隐含的那些额外义务并没有被机械强制。这个缺口是真的，把它讲出来比讲口号重要——代码做的是"单向检查"，而"永远不能更轻"会声称得比代码更多。

声明 thin 也不是绕过验证的捷径。声明必须一次带齐四样东西：显式的声明本身、逐信号的耦合检查清单、对跳过引入什么风险的说明、以及一份仍然包含 P5 和 P6 的 phase 列表。缺任何一样，gate 就 exit 1，你静悄悄回退到 standard。薄路径薄的是仪式——它从不薄化验证。

这部分值得你偷走，哪怕你永远不碰 Agateon。它是一条通用性质：**流程深度的声明应该能被证据检查，而检查要朝更严的方向失败。** 大多数流程争论死在这里：分歧不再是"我们需要这个吗"，而是"这是五行证据，哪一行是错的？"

## 它到底花多少

现在说最要紧的数字，是从我们自己的工作区量出来的，不是估的。`agate-workspace/tasks/` 里 37 个任务：

| 指标 | 中位数 | 备注 |
|---|---|---|
| 日历跨度 | 约 21 小时 | 该任务首个到最后一个 commit |
| commit 数 | 13 | 最多 44 |
| 阶段产物行数 | 约 6700 | 跨约 37 个 `P*.md` 文件 |
| 派发重试 | 19/37 个任务 | 至少一条非空 retry 记录 |

这个跨度不是 agent 的运行时间。它是日历时间，大头在等人来看一眼。所以协议的真实价格不是算力——是你的注意力，花在沿途的 gate 上，而不是花在最后那一次 review 里。如果你的任务是那种你反正只看一遍的两小时改动，这笔交易是净亏。

价值那侧，从 append-only 账本读出来，比推销话术说的要小、也更怪。记录的 119 次 gate 运行里，**115 次以该 phase 的通过码结束**（多数 phase 是 exit 2，P4/P7/P6.5 是 exit 0）、1 次带警告通过、**3 次 exit 1——真拦截**。exit 2 值得说明一句：对多数 phase 来说它就是通过码，不是跳过。真正被 gate 拦下过的只有 2 个任务——而诚实的母数是那 14 个有账本的任务，因为 append-only 事件账本是这个仓库走到中途才引入的。这个比例我们之前写过，图景没变：一道很少开火的 gate 是在按设计工作，但谁都不该指望它省下惊天动地的一大笔。你买的是对那些预见不到的失败的覆盖——自报的计数器读数是空的、某个 phase 悄悄给自己降级、评审者和作者共享同一个盲区。

## 什么时候这些你都别用

- **一次性脚本和小修复。** 如果整个改动就是你会花五分钟看完的一个 commit，八阶段流水线是纯开销。写脚本、跑测试、发出去。
- **没有机器可校验信号的活。** 协议的杠杆来自 gate 读 exit code 和 diff。如果你的任务的"完成"定义是"设计文档读起来不错"，gate 就没有东西可抓——你在为那些帮不上忙的部分付仪式成本。
- **探索和 spike。** 研究类任务没有验收标准可验，给它算分算出来的档位毫无意义。给 spike 定时，扔掉，再把真正的任务放进 gate 里跑。
- **你付不起那份注意力的时候。** 成本是人不是算力。如果这周没人能看 gate，gate 就变成一条你会跳过的队列——而被跳过的 gate 比没有 gate 更糟，因为产物里仍然记着"验证过了"。
- **你需要跨机器可复现的时候。** 路由和算分配置是刻意做成逐机、机会式的。如果你的要求是两个工程师得到逐字节相同的流水线，这个设计选择就是跟你对着干。

## 五个问题的清单

在采用任何东西之前（我们的或别人的）先答这五个：

1. **你的"完成"作为一个机器可校验信号长什么样**——一个 exit code、一个 diff、一个计数？说不出来，就没有协议能救你。
2. **你的 agent 现在多久回来一次是错的**，以及你怎么知道的？第二个问句答不上来，你就是在凭记忆决策——正是算分机制要防的那个错误。
3. **一次坏产出在你的场景里值多少**：重跑一次、构建坏掉、生产事故、还是客户看得见的谎言？
4. **谁来读这些 gate？** 说出那个人的名字。如果是"没人，我们信绿勾"，那你买的是仪式，不是验证。
5. **为了采用它，你得删掉什么？** 如果诚实的答案是"我们现有的测试套件"，停——gate 放大你已有的信号，它们不创造新信号。

如果第 1、2 题答得干脆，第 3 题很贵，那么这套协议能自己赚回来。如果第 3 题很便宜，或者第 4 题说不出名字，跳过它：那种活，一个脚本加一次 code review 就是正确答案。
