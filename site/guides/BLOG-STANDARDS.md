# Agateon 博客编制规范

> **本文档是 Agateon 博客内容的质量唯一权威源。** 任何 agent 在接到"写/改/发博客"任务时，
> 必须先读本文档 + `CONTRIBUTING.md`（机械流程，索引见 `README.md`），再动手。
> 发布前必须通过第 7 节的独立评审 gate，否则不发布。

## 1. 定位与读者分层

- 站点文章（`site/blog/`）是**唯一母稿**，面向三类读者：
  - dev.to（国际技术社区）：英文为主，技术深度接受度高
  - Hacker News：英文，观点与验证导向，**反营销**
  - 微信：中文，通俗，短
- **站点正文硬标准：图文并茂、详略得当、通俗易懂。** 这是所有平台共享的母稿标准，
  cross-post 只在发布时按平台调整语言/长度，不改母稿质量。
- **一篇文章只讲一件事**。讲不清就拆成多篇，不在一篇里塞多主题。

### 1.1 读者收益门槛（2026-09-19 起，选题硬门槛）

> **背景**：2026-09-19 用户反馈——"你写的 blog 都围绕自身 agate-workspace 数据，甚至目标或建议
> 决策也是针对 agateon；别的项目用的时候，压根对你在 dogfooding 怎么搞的不关心，人家就关心自己，
> 就关心用 agateon 能不能带来收益"。根因：把**素材来源**（我们自己的数据，真实且好验证）当成了
> **主题**（读者能得到什么）。dogfooding 数据是好**论据**，不是好**主题**。

**选题必须先过这一问，答不出就不写：**

> **读者看完这篇，能拿走什么、用在他自己的项目里？**
> （不是"知道了 Agateon 怎么做"，而是"我的返工率/评审时间/被骗次数会怎么变"）

- **收益必须是读者的，不是我们的**。"我们的任务中位 21 小时"是我们的成本；
  "你的 agent 在长任务上返工率会降"才是读者的收益。前者可以当论据，不能当主题。
- **机制必须可搬走**。读者不装 Agateon 也应该能拿走点什么（一条规则、一个检查、
  一个决策判据、一个可复制的对照实验）。纯"我们的实现细节"不算收益。
- **建议/清单必须以读者为坐标**。写"你该不该上 Agateon"是产品推销；
  写"你的 agent 工作流该用多重的流程、怎么判断"才是通用产品——Agateon 只是其中一种实现。
- **自指数据有配额**。`TAG####`、`agate-workspace/`、我们自己的账本数字，一篇里出现的位置
  必须**服务于读者论点**；不能整段充当主题。评审时若发现"把内部数据当主题"判 FAIL。

**自检句式**（写进 P1/选题卡）：
1. 读者是谁（哪类团队/什么场景）？
2. 他现在怎么做，痛点是什么？
3. 看完这篇他会改变什么行为？
4. 这条建议脱离 Agateon 还成立吗？（不成立 → 是推销，不是文章）

## 2. 风格（Voice）

- **范本：post-01**（`site/blog/20260826/post-01-retry-self-authorization.md`）——诚实复盘风。
- 第一人称、具体、诚实，**包括主动承认失败与局限**。
- 禁用：营销腔、形容词轰炸（revolutionary / amazing / cutting-edge）、夸大、虚假确定。
- **用证据说话**：Agateon 的特色是"一切可验证"——文内链接真实代码 / 任务 / commit，
  读者点开能复现，不接受只给结论不给路径。
- 主动暴露"仍不确定的地方"（post-01 的 *What's still open* 是固定模板）。
- 语气：工程师对工程师，不是厂商对市场。

### 2.1 活人感硬规则（反 AI 腔，2026-09-05 起）

结构完美、每段收在警句上、节奏均匀——这些"太好了"本身就是 AI 味。初稿后必须做一遍
**voice pass**，逐条对照：

- **警句密度**：全文最多 2 句"可摘引的对称句"。写初稿时想放在每段结尾的警句，砍到只剩最好的。
- **节奏不均匀**：段落长短必须拉开——有 5 句的段，也允许只有 1 句的段。连续三段等长 = 重写。
- **列表克制**：连续加粗引导词的 bullet 列表全文 ≤2 处；能写成散文的不拆列表。
- **第一人称现场**：每篇至少 1 处具体到能看见的场景（几点钟、我在哪、第一反应是什么），
  不是"我们注意到"这种悬空的第一人称。
- **允许不完美**：每篇至少 1 处真实的不确定、自我怀疑或岔路（"我们先试了 X，错了，因为…"）。
- **voice pass 操作**：初稿完 → 通读一遍 → 圈出所有对称句和"每段结尾的 punchline" →
  按上面配额删 → 重读节奏。

## 3. 结构

- **frontmatter 四件套必须齐全**：`title` / `date` / `description` / `tags`。
- **开头 hook（≤3 句）**：痛点或问题开场，直接抓住人，不铺垫。
- 中段骨架：机制 → 发现 → 修复 → 验证，每段配图或 mermaid。
- 结尾：一般规律总结（"if you're building X, check Y"）+ 相关链接。
- 长文（>800 词）必须有 TL;DR 或章节摘要。
- 标题：具体、信息密度高、非 clickbait（要在 HN 上站得住）。
- 每节聚焦，禁止"顺便讲一下"的岔路。

## 4. 详略（详略得当）

- **值得深写**：机制如何工作、失败模式、修复逻辑、验证（我们怎么测的）。
- **值得砍**：流程琐事、内部 task ID（除非读者需要它来复现）、版本号流水账。
- **判断标准**："这句话删掉读者还能不能完全理解？能就删。"
- 代码 / 命令给真实路径，不写伪代码糊弄。

## 5. 通俗（通俗易懂）

- 术语首现必解释（"gate" 第一次出现用一句话说清）。
- 短句化；一段一个意思。
- 给具体例子，不用抽象描述代替。
- 不过度浅化：读者是工程师，"git" 不必解释；但项目特有的机制必须讲透。
- 中文版遵守 CJK-Latin 空格、全角标点（见 writing-markdown skill）。

## 6. 配图规范（重点）

### 6.1 原则

- **图文并茂**：关键概念一图一意；流程用 mermaid；不装饰性凑图。
- 每张图必须服务于理解，删掉会损失信息，否则不画。

### 6.2 类型与尺寸

| 类型 | 尺寸 | 要求 |
|------|------|------|
| 封面（必须） | 1200×630 | 主题 + 一句话副题，vision 质检必过 |
| 正文插图 | ~900×520 | 一图一意 |
| 流程图 / 时序图 | mermaid 代码块 | 可版本控制、可搜索，不用图 |
| 对比图（before/after） | ~900×520 | 范本：illustration-before-after-fix.svg |

### 6.3 风格

- **品牌 5 色板内**（Ink `#1A1A18` / Paper `#FAF9F4` / Gate teal `#1D9E75` / coral `#D85A30` /
  purple `#7F77DD`，见 `docs/brand/README.md`）。
- **几何矢量风**：闸口（gate）、checkpoint、agent 图标——与现有 3 张封面/插图同一视觉语言。
- 禁：投影 / 渐变 / 描边 / 照片 / emoji 作主视觉 / 超出色板。
- 图上文字要**少而大**（图在移动端会缩小，字多了看不清）。

### 6.4 生产流程（agent 执行）

```
1. 定意图：这张图只讲一件事
2. 手写 SVG（品牌几何风，自己写，不用 AI 生图——本环境无生图能力，
   且品牌矢量风 AI 栅格图会违和）
3. headless Chrome 渲染 PNG（封面 1200×630、正文 ~900×520）
4. vision-engine 质检（必须，见 6.5 checklist）
5. 不合格 → 回 2 重画 → 再质检，循环直到 pass
6. 写 alt text（描述内容，不只"图片"）
```

### 6.5 配图质检 checklist（vision-engine 执行）

- [ ] 图表达的意思 == 图注 / 正文描述
- [ ] 图上文字完整、无溢出、无错别字（用 `ocr` 角色查）
- [ ] 颜色都在品牌 5 色板内
- [ ] 缩到 400px 宽仍可读（细节没画太小）
- [ ] 比例正确（封面 1200×630）

## 7. 评审 gate（独立评审 → 迭代通过）

> **§1.1 读者收益项（2026-09-19 起必评）**：评审必须独立回答——(a) 这篇的**主题**是读者的收益
> 还是我们自己的做法？(b) 读者不装 Agateon 能拿走什么？(c) 有无"把内部 dogfooding 数据当主题"
> 的段落（列出位置）？(d) 建议/清单是否以读者为坐标（还是变相的"该不该用 Agateon"）？
> 任一项不成立 → FAIL。

> **发布前必须过独立评审，否则不发布。** 这是硬 gate。

- **独立评审** = 一个**全新 subagent**（无写作上下文、无作者滤镜），拿本规范做 checklist
  审草稿——judge 独立于执行者，这正是 Agateon 自己的哲学。
- **评审 checklist**（评审 agent 逐项 PASS / FAIL + 具体修改意见）：

  - [ ] 风格：诚实、无营销腔、用证据说话、主动暴露局限
  - [ ] **活人感（§2.1）**：警句 ≤2、段落节奏有起伏、有第一人称现场细节、列表克制——
        "每段都收在警句上 / 全文节奏均匀" 判 FAIL
  - [ ] 结构：hook ≤3 句、机制→发现→修复→验证骨架、结尾总结、长文有 TL;DR
  - [ ] 详略：值得深写的有深度，可删的都删了
  - [ ] 通俗：术语首现解释、短句、有例子
  - [ ] 配图：封面必须有且过了 6.5 质检；每张图一图一意、色板内、alt text 完整
  - [ ] 事实核验（硬项）：文内**每个链接都真实存在**（评审 agent 实际检查）、
        代码路径 / 版本号 / mermaid 语法正确
  - [ ] frontmatter 四件套齐全、build 通过
  - [ ] **中文版（若在本次范围）**：按 §9 人工重写而非机翻——发现翻译腔
        （逐句对译痕迹 / 禁用词表命中 / 英语句法直译）判 FAIL；数字与 EN 严格一致

- **流程**：作者写稿 → 评审 subagent 审 → 不过 → 作者按意见迭代 → 再审 →
  **pass 才走 git 管线上线 + cross-post**。

## 8. 作者自检清单（交评审前先自己过一遍）

- [ ] **§1.1 读者收益四问**已答（读者是谁/痛点/行为改变/脱离 Agateon 是否成立）
- [ ] 全文自指数据（TAG####、agate-workspace、我们的账本数字）都在**服务读者论点**，
      没有整段充当主题

- [ ] frontmatter 四件套齐全
- [ ] `cd site && npm run build` 通过
- [ ] 每张图过了 6.5 vision 质检
- [ ] 所有链接 / 路径实测存在
- [ ] 风格 / 详略 / 通俗自评达标
- [ ] **voice pass 已做**（§2.1：警句配额、节奏、第一人称现场逐条过）
- [ ] **zh 重写稿已完成并按 §9 自查**（无翻译腔、数字与 EN 一致、链接指向 /zh/blog/）

## 9. 中文版（重写不翻译，2026-09-05 起）

> **zh 正文一律人工重写，禁止机翻直接发布。** 机翻保英语句法，产出的是精确的翻译腔
> （长定语链 / 被动式 / "进行 X" / "揭示了"），读感完全不是人写的。i18n 脚本已按此改造：
> 正文只做存在性检查与告警，**绝不生成、绝不覆盖**；配图翻译与索引生成照常自动。

### 9.1 流程

1. EN 过完评审 gate 定稿后，以中文母语工程师视角**从头重写**——保主张、数字、链接、
   代码块、结构骨架，句子全部重造。
2. zh 配图：脚本可自动翻译 SVG 短标签（短文案机翻可接受），但发布前人工过一遍词感
   （"您"→"你"、"进行解读"→"读"、"仅存在于"→"只活在"），标点用全角。
3. 重写稿纳入评审范围：评审按 §7 中文版项核翻译腔。

### 9.2 重写规则

- **重写的是论证，不是句子**：允许语序重排、段落合并拆分、例子本地化；不允许逐句对译。
- **短句优先**：一句一个信息；EN 的一句话可以拆成中文两三句。
- **禁用词表**（翻译腔信号，命中即改）：揭示 / 旨在 / 值得注意的是 / 总而言之 / 综上所述 /
  "进行 + 动词"（进行验证→验证）/ "仅存在于" / "很大程度上" / 被动句堆叠。
- **语气词少量允许**：说白了 / 其实 / 挺离谱的 / 答不上来——每篇 ≤4 处，别撒味精。
- **技术名词保留 EN**：agent / gate / hook / commit / JSONL / exit code 等不硬翻；
  CJK-Latin 之间加空格。
- **事实零漂移**：所有数字、链接、代码与 EN 严格一致；**站内链接指向 `/zh/blog/`**；
  外链不变。
- **标点**：全角标点；破折号用"——"；数字与 EN 术语周围留空格。
- **图片 alt text 也要人话重写**，不直译。
