## 摘要（结论前置）

1. **DAG 化（跨阶段流水）在数学上成立**，收益上限 = `Σ_phases max_tracks(w) − max_tracks Σ_phases(w)`，**完全由「同一任务内、切片之间」的耗时方差决定**。切片同构或单切片时收益为零。

2. **收益的前提被证实、收益的空间被证伪**：从 `wf(Txxx-Pn{batch})` 批级 commit 时间戳可还原批级耗时，16 个多批次阶段的**变异系数 CV 中位 0.81、81% 阶段 CV>0.5**——同阶段内确实存在显著异构。**但异构 ≠ 可流水**：唯一核验的 TAG0034 案例中，显著差异（P4a 410 min vs P4b 24 min）是**设计阶段的真依赖**（`serial: true`，同文件分层实现），不可压缩。

3. **DAG 收益被三重天花板压缩**：
   - **天花板 1（真依赖）**：如上——批次差异可能源自设计依赖，而非门禁空转
   - **天花板 2（验证不可切片）**：5 个可核验任务的 `gate_commands.P5` **全是全量套件**（`pytest agate/tests/`），P5 卡片明确「全量测试套件属资源密集型**默认串行**」「修复后必须重跑**全量**」——**不存在切片级验证单元**
   - **天花板 3（judge 全局屏障）**：P6.5 judge 以 fresh context 重验**全部** BDD，本质任务级端到端验证，不可流水

4. **收益池已枚举：11/34 任务（32%）**——判据是「`static-batch` 且 ≥2 批**且无串行声明**」（字面 `static-batch` 且 ≥2 批为 13，需再排除 `TAG0034` 的 `serial: true` 与 `TAG0022` 的正文串行声明）。且这 11 个的批次**现状下已并行**。**DAG 的可实现收益空间在现有样本中接近于零到很小**，而它的成本是协议内核级（状态 schema + gate + hook + 审计链 + 破坏性变更迁移）。

4b. **跨项目验证（PeekView 产品项目）**：结构前提更充分——新格式任务多切片率 **78%**（7/9）vs agateon **32%**（11/34）；**但切片级验证单元在两类项目中都几乎不存在**（PeekView 真分包 P5 仅 **2/63 = 3%**，agateon 0%）。且 PeekView 的 `make test-quick` 名为 quick **实为全量后端测试**（1068 tests）——与 agateon 的全量套件同构。**结论：收益瓶颈不是"没有切片"，而是"没有可流水的验证单元"**（详见 §4.7）。

5. **另有独立瓶颈**：13 个有事件流的任务中，跨度 194.2 小时里 **73.8% 的耗时位于 >3 小时的间隔中**，>12h 的 4 个间隔独占 41.2%。**会话/人工节奏是另一个（可能更大的）瓶颈**，且它不受并行化改善。

6. **阶段内并行早已落地且在用**：11 个 `static-batch`（≥2 批）任务各有 2–11 个 P4 派发上下文，且 commit message 直接标注「N 批并行」。协议并非「纯串行」——串行的只是**阶段之间**。

7. **阶段集（P0-P8）可扩展性的真实成本集中在三处**：① `phases.schema.json` 的 `enum` 硬锁（且 `additionalProperties: false`）；② `check-gate.py` 的 10 个手写 `gate_pN()` + 硬编码 `handlers` 字典——`phases.yaml` 的 `gates` 字段只是**散文描述**，真实判定在手写函数里；③ **数字序号假设**（三处 `re.search(r"[0-9]+", phase)`）——**非数字阶段名（`p-alpha`）会让回退检测与状态转移判定静默失效**。另发现 gate 对未知阶段 **fail-open**（`exit 2` = 通过码）。

8. **阶段集可扩展有既有范式可循**：协议**已支持自定义角色**（`assets/templates/custom-role.md`：`role_id` 自由填写 + `phases: [...]` 声明适用阶段），而阶段本身仍是 enum 硬锁 + 10 个手写 gate 函数——**阶段扩展的成熟度显著低于角色扩展**。最自然的路径是**把角色的声明式范式迁移到阶段层**（协议定义 gate 类型，项目声明阶段实例），而非发明新机制。

9. **跨项目验证（PeekView，94 任务）**：产品项目的多切片率更高（新格式任务 **78%** vs 32%），但**切片级验证单元在两类项目中都稀缺**（3% vs 0%）——**瓶颈不是"没有切片"，而是"没有可流水的验证单元"**（§4.7）。

10. **正确的度量是"关键路径弹性"而非批间方差**（v4 采纳外部评审）：两个可完整重建依赖的任务弹性都 ≈0——TAG0034 因真依赖、TAG0033 因全量验证屏障（§4.8）。

11. **MVWU（最小可验证工作单元）的雏形已存在于既有实践**（v4 新增）：**25 条批级 commit 已系统性携带批级测试证据**（`pytest -k tag0034 = 90/0 全绿`）。缺的不是新机制，而是三件制度化工作：证据标准落点、消费 gate、批→测试映射声明（§4.9）。

12. **MVWU 的四不变量几乎已全部落地**（v5 新增，两轮评审共同指向）：`I1 Boundary` = 批级 commit 文件集（git 原生）；`I2 Verification` = 批自带测试文件（`test_tag0034_p4c.py`）+ 批自带证据（`P4-implementation-P4c.md`）；`I3 Provenance` = `check-p6-provenance.py` 七道审计（成熟）；`I4 Composability` = 任务级拆分实践。**MVWU 不需要新子系统，只需把事实写成声明**——最小改动集为 `batches[].tests_filter` 声明化 + 批级证据结构化落点（§11.2），零协议内核改动。

13. **度量修正（采纳评审）**：11/34 只是**当前快照**，会随 MVWU 落地而失效（分母改变）。决策公式应改为 **MVWU 级流水弹性** `E_pipeline = (T_barrier − T_optimal)/T_barrier`，超过阈值才触发 DAG 研究（**Research Trigger**）——DAG 不进 roadmap 功能列表（§11.5）。

14. **I1 可归属性的量化实证（v6 新增）**：**16 个多批任务中仅 2 个（13%）** 采用逐批 commit（I1 可机械验证），**14 个（87%）为合并 commit**（不可归属）。这与 §4.5「验证不可切片」是**同一结构性约束的两种表现**——**并行执行 ≠ 可独立验证，也 ≠ 可独立归属**。由此产生一个需用户裁决的取舍：保持合并 commit（保留原子性，I1 覆盖 13%）vs 改逐批 commit（I1 覆盖多数，失去原子性）（§11.7）。

15. **建议（v6 重排）**：P0 = 阶段序显式化 + fail-closed ＋ 活动遥测（缺口极小）＋ **MVWU 最小改动集试点**；P1 = 工作保持调度、任务级拆分；P2 = 两张图（研究）；**真 DAG 降为条件触发的 Research Trigger**。战略上 agateon 的护城河是 **Verification Plane**（Control Plane 将商品化），而 **MVWU 是其基本原子**（§10、§11）。

## 1. 问题定义

### 1.1 现状模型：阶段屏障（Barrier-Synchronous）

```
P0 ──▶ P1 ──▶ P2 ──▶ P3 ──▶ P4 ──▶ P5 ──▶ P6 ──▶ P6.5 ──▶ P7 ──▶ P8 ──▶ READY
       │      │      │      │      │      │
       └──────┴──────┴──────┴──────┴──────┴── 每阶段一道全局屏障（gate）
```

- `.state.yaml` 的 `phase:` 是**单标量**——任一时刻只有一个阶段在飞
- 阶段推进条件：`check-gate.py {phase}` 通过（`phases.yaml` 的 `gate_pass_exit` 定义通过码）
- 阶段内**可以**并行（模式 2/3，按 package 拆批），但**阶段之间不能重叠**

### 1.2 设想模型：切片流水线 / DAG

```
P1: [req-front] [req-back] [req-db] ──merge──▶ P2 ──▶ ┌ P3-a→P4-a→P5-a ┐
                                                      ├ P3-b→P4-b→P5-b ┤─merge─▶ P6...
                                                      └ P3-c→P4-c→P5-c ┘
```

- 并行单位从「阶段内的包」变为「贯穿阶段的切片」
- 屏障只保留在 merge 点；切片完成即释放资源、可再并发其他工作
- 进一步设想：**阶段集本身不固定**——除 P0-P8 外可有 `p-a`/`p-b`/`p-alpha` 等自定义阶段（软件工程只是典型 workflow 之一）

### 1.3 本文回答的问题

| # | 问题 |
|---|------|
| Q1 | DAG 化的理论收益是多少？边界在哪？ |
| Q2 | 实测数据支持这个收益吗？瓶颈真是屏障吗？ |
| Q3 | 落地要改哪些机制？成本分布如何？ |
| Q4 | 阶段集可扩展（非数字阶段名）独立成本是多少？ |
| Q5 | 有没有更低代价的等价路径？ |

### 2.1 数据来源

| 来源 | 内容 | 覆盖 |
|------|------|------|
| `agate-workspace/tasks/*/gate-events.jsonl` | 哈希链事件流：`state_transition` / `gate_run` / `judge_verdict`，带 ISO 时间戳 | 13 个任务 |

| `agate-workspace/tasks/*/P{3,4,5,6}-dispatch-context-*.md` | 批级派发证据（并行度 proxy） | 抽样 |
| `agate/rules/phases.yaml` + `schema/phases.schema.json` | 阶段图与校验约束 | 全量 |
| `agate/scripts/*.py` | 阶段硬编码面 | 全量扫描 |

**事件规模**：`state_transition` 136 条、`gate_run` 111 条、`judge_verdict` 40 条，13 个任务。

### 2.2 测量口径与**其局限**（必读）

现有事件流只能回答"**两次 gate/转移之间隔了多久**"，不能回答"**agent 在这段时间里是否在算**"。本文采用两个口径：

- **口径 A（事件间隔）**：相邻事件的原始时间差
- **口径 B（会话聚类）**：以 30 分钟为阈值把事件聚成"会话窗口"，窗口内视为连续工作，窗口之间的间隔视为非工作

**口径 B 的已知偏差**：
1. 会把「agent 持续跑 45 分钟的 subagent」误判为"非工作"（因为它不产生事件）
2. 会把「人工 5 分钟内快速批复」误判为"工作"
3. 因此 **7.9% 这个"活跃占比"应理解为下界**，真实 agent 工作时间介于 7.9% 与 100% 之间，**无法从现有事件流确定**

> **重要的口径补充（v2 修订）**：v1 初稿据此判定"关键路径优化缺少靶心"，该结论**已被部分推翻**——批级耗时**可以**从 `wf(Txxx-Pn{batch})` 批级 commit 的时间戳还原（见 §4.3），因此"**切片间耗时方差**"这一 DAG 收益的关键量**是可测的**。
> 仍**不可测**的是：**agent 活跃时间 vs 人工等待时间的精确切分**（需要新探针，见 §9.2）。这两者是不同的问题——前者决定 DAG 收益，后者决定"优化方向该不该是并行化"。

## 3. 实测发现

### 3.1 时间去哪了：73.8% 在长间隔里

274 个事件间隔的分布（13 任务合计 194.2 小时）：

| 间隔区间 | 个数 | 个数占比 | 时长(h) | **时长占比** |
|---------|-----:|--------:|--------:|-----------:|
| <1 min | 156 | 56.9% | 0.2 | 0.1% |
| 1–5 min | 9 | 3.3% | 0.4 | 0.2% |
| 5–15 min | 37 | 13.5% | 5.9 | 3.1% |
| 15–30 min | 24 | 8.8% | 9.4 | 4.8% |
| 30–60 min | 18 | 6.6% | 11.8 | **6.1%** |
| 1–3 h | 14 | 5.1% | 23.2 | **12.0%** |
| 3–12 h | 12 | 4.4% | 63.2 | **32.6%** |
| >12 h | 4 | 1.5% | 80.0 | **41.2%** |

**读法**：
- **事件是"成簇"发生的**（56.9% 的间隔 <1 分钟）—— gate 通过 → commit → 转移几乎同时
- **耗时集中在少数长间隔**：>3 小时的 16 个间隔（占个数 5.9%）吃掉 **73.8%** 的总时长
- 单看这条分布，**优化"阶段间的同步开销"几乎不会改变总时长**

**阈值敏感性检验**（结论是否依赖 30 分钟阈值）：

| 阈值 | 长间隔个数 | 时长(h) | 占总时长 |
|------|----------:|--------:|--------:|
| >10 min | 91 | 191.4 | **98.5%** |
| >15 min | 72 | 187.7 | 96.6% |
| >30 min | 48 | 178.3 | 91.8% |
| >60 min | 30 | 166.4 | 85.7% |
| >120 min | 19 | 150.6 | **77.5%** |

**即使把阈值提高到 120 分钟（只算 2 小时以上的间隔），仍占 77.5%**——"耗时集中在稀疏的长间隔"这一结论**对阈值不敏感**，是稳健的。

**分布形状**（P50=0.3 min、P75=18.2、P90=70.8、P95=225.5、P99=1010.1）：
典型的**重尾分布**——中位数极小（多数事件成簇爆发），但尾部极长。这意味着：
- 用**均值**描述阶段耗时会严重误导（均值 42.5 min vs 中位 0.3 min）
- 长尾由**少数超长等待**构成，且这些等待**不在 agent 的控制范围内**（会话边界/人工决策）

### 3.2 阶段耗时分布：方差极大

| 阶段 | 样本 | 中位(分) | 均值(分) | 最大(分) |
|------|-----:|--------:|--------:|--------:|
| P0 | 6 | 91.8 | 274.0 | **1010.1** |
| P1 | 17 | 34.5 | 72.4 | 336.1 |
| P2 | 18 | 19.8 | 62.5 | 797.0 |
| P3 | 16 | **100.9** | 254.8 | **1858.3** |
| P4 | 20 | 19.4 | 58.4 | 434.7 |
| P5 | 18 | 10.3 | 93.6 | 1132.2 |
| P6 | 16 | 19.7 | 39.0 | 256.7 |
| P7 | 8 | 6.6 | 6.4 | 16.0 |
| P8 | 4 | 10.5 | 12.5 | 28.7 |

**观察**：
- **P3 中位最高（100.9 分）**，且尾部最长（1858 分）——与"测试设计是瓶颈"的直觉一致
- **P7 极快且稳定**（中位 6.6 / 最大 16 分）——一致性检查本身不是瓶颈
- **均值远大于中位**（P0: 274 vs 91.8；P3: 255 vs 101）——**分布严重右偏，少数超长样本拉高均值**
- **方差来源是"任务之间"，不是"任务之内"**：同是 P3，有的 20 分、有的 1858 分。这对 DAG 收益的含义见 §4.3

### 3.3 返工率：意外的低

- `state_transition` 事件 136 条，构成 **123 个阶段间隔**；其中**反向（返工）转移 1 次**，返工率 **0.8%**
- 唯一一次：TAG0033 `P5→P4`（192.6 分钟）

**这修正了一个常见假设**：屏障的主要价值常被论证为"拦截返工"，但实测返工极少（样本内）。屏障的**真实价值更可能在"防 by-design 红推进"**（DEBT0039 的教训类型），而非"降低返工频率"。

> 注意：样本仅 13 个任务，返工率 0.8% 的置信区间很宽；且"返工"此处只统计**阶段反向转移**，不含阶段内的重试轮次（`retries[Pn]`）。

### 3.4 并行现状：阶段内并行早已在用

派发上下文文件数（批级并行的直接证据）：

| 任务 | P3 | P4 | P5 | P6 |
|------|----|----|----|----|
| TAG0030-acceptance-blindspot | 1 | **5** | 1 | 1 |
| TAG0033-codex-cmdstream-adapter | 1 | **8** | 3 | 1 |
| TAG0034-dispatch-routing | 1 | **5** | 1 | 1 |

`dispatch_plan` 声明样例：
```
{mode: static-batch, parallel_limit: 4, batches: [...4 批...]}
{mode: static-batch, parallel_limit: 8, batches: [...8 批...]}
{mode: static-batch, parallel_limit: 3, batches: [...3 批...]}
```

**直接的 commit 级证据**（批次数与"并行"字样直接写在 commit message 里）：

| 任务 | commit message 摘录 | 含义 |
|------|--------------------|------|
| TAG0017 | `wf(TAG0017-P4): 实现（5 批并行 + review-fix + self-gate 修复）` | 5 批**并行** |
| TAG0023 | `wf(TAG0023-P4): 实现完成——4批并行（A retries对应性/B roadmap反查/C git版本差异根因修复/D写时自检）` | 4 批**并行** |
| TAG0031 | `wf(TAG0031-P4): 实现——三簇并行 + debt 登记收尾` | 3 簇**并行** |

**注意**：这些任务的多个批次**只有一个 P4 commit**——这正是"并行 → 各自产出 → 主 Agent 汇总统一 commit"（`dispatch-protocol.md:618` 模式 3 的定义）的直接体现。

**结论**：协议已经具备"阶段内按包并行"，`parallel_limit` 可覆盖默认值 3，且**实测中已被实际使用**（5 批/4 批/3 簇并行）。**尚未具备的是"阶段间流水"**——而 §4.6 表明这恰是收益池被三重天花板压缩后的残余部分。

### 3.5 短任务可以极快穿越全部阶段

TAG0030 实测：**单一 1.7 小时窗口内走完 P2→P3→P4→P5→P6→P7→P8**：

```
2026-09-03 20:45:50  P2→P3
2026-09-03 20:59:53  P3→P4
2026-09-03 21:46:09  P5→P6
2026-09-03 22:13:17  P7→P8     ← 全程 87 分钟
```

**含义**：阶段屏障的固定开销**并不大**——小任务的 P0-P8 全链可以在 1.5 小时内跑完。长耗时来自任务规模与人工节奏，不是阶段数量本身。

## 4. 收益模型：DAG 到底能省多少

### 4.1 公式

设任务有 *k* 个切片、*p* 个阶段，切片 *i* 在阶段 *j* 的耗时为 `w[i][j]`：

| 模型 | 总时长 |
|------|--------|
| 现状（屏障；阶段内可并行） | `T_barrier = Σ_j max_i w[i][j]` |
| 流水线（切片贯穿） | `T_pipe = max_i Σ_j w[i][j] + merge_cost` |
| **理论收益** | `G = Σ_j max_i w[i][j] − max_i Σ_j w[i][j] − merge_cost` |

### 4.2 收益边界

| 情形 | 收益 |
|------|------|
| 单切片（k=1） | **G = 0**（退化为串行，无并行可言） |
| 各切片各阶段耗时相同 | **G = 0**（`Σmax = maxΣ = k·p·w`） |
| 切片间耗时异构 | G > 0，最大可达 `(k−1)·min_j(...)` 量级 |
| merge 成本 ≥ 收益 | G ≤ 0（负收益） |

**关键判据**：**`G > 0` 要求同一任务内、不同切片在**同一阶段**的耗时存在显著差异**。

即使假设批次真独立，**验证阶段本身也不可流水**：

**证据 1 — `gate_commands.P5` 是**全量**套件（跨任务核验，非单例）**：

| TAG0034 | `python3 -m pytest agate/tests/ -q --tb=no`（另含 consistency / events / routing_schema） |

**全部 5 个可核验任务的 P5 都是全量套件（整目录或全分类组合），无一是逐包范围**——"切片 A 只跑 A 的测试"这种模式在现有 `gate_commands` 里**不存在**。

**证据 2 — P5 卡片明确定义了范围与资源约束**（`phase-cards/P5-verification.md`）：
- 第 26 行：「修复后重跑 `gate_commands.P5` **全量**（T027 教训：修复可能引入回归，不能只检查修复项）」
- 第 58 行：「**全量测试**：P5 阶段应运行**全量测试套件（含非本任务测试）**」
- 第 115–124 行：P5 **可按包拆分并行**，但——
  > 「`gate_commands.P5` **常是全量测试套件**（含 xdist 多进程）或 E2E 浏览器命令，属**资源密集型默认串行**……无法隔离即串行（安全默认值）」

**含义（对 DAG 收益的第三重削弱）**：

| 限制 | 后果 |
|------|------|
| P5 验证是全量套件 | 切片 A 的"验证"与切片 B 的"验证"**跑的是同一套命令**——**不存在"切片级验证"**，因此**无法"切片 A 完成即验证 A"** |
| 资源密集型默认串行 | 即便 P2 声明了多包，P5 仍默认串行 |
| 全量重跑是硬要求 | 每次修复后必须重跑全量（防回归），**流水化会与这条要求冲突** |

**这是 DAG 收益的第三个天花板**（前两个：§4.4 真依赖、§6.5 judge 全局屏障）：

> 流水线的价值在于"切片完成即可独立验证"，但 agateon 的 P5 是**任务级全量验证**——**没有可流水的验证单元**。要流水，必须先有"切片级验证 + 最终全量验证"的两级验证设计，而后者（全量）**无论如何都是屏障**。

**三重天花板叠加后的收益估算**：
```
名义收益（Σmax − maxΣ）
  − 真依赖批（§4.4，TAG0034 案例：100% 削减）
  − 全量验证不可流水（§4.5，验证阶段完全不可流水）
  − judge 全局屏障（§6.5，尾部 P6/P6.5/P7 不可流水）
  = 残余收益：仅"已声明可并行、真独立、且其验证可切片"的批次 → 规模很小
```

### 4.8 关键路径弹性（Critical-path Elasticity）——比"批间方差"更正确的度量

外部评审指出 §4.3 的度量偏差，**成立**：批间耗时方差（CV）只是 DAG 收益的 **proxy**，正确的度量是——

> **若移除某条依赖边或屏障，关键路径实际缩短多少**（弹性），而非"批耗时不均匀"。

对本报告可完整重建依赖关系的两个任务做**迷你关键路径重建**：

| 任务 | 依赖边（实证） | 屏障移除后关键路径 | 弹性 |
|------|--------------|------------------|------|
| TAG0034 | P4a→P4b（同文件，`serial: true`）；P4b→P4c（共享契约由 P4a 固化） | 依赖链不变：410+24+8=442 min | **≈0** |
| TAG0033 | `adapter-core` ∥ `protocol-docs`（文件不相交）——**但 P5 是全量套件，必须在两批完成后运行** | P5 起点不由批序决定，由全量验证决定 | **≈0** |

**两个可重建案例的弹性都 ≈ 0**——原因不同（前者真依赖、后者全量验证屏障），结果相同。**这把 §4.6 的"收益池小"从统计判断升级为机制判断**：即便在候选池任务里，被屏障"挡住"的批也要么真依赖、要么无法独立验证。

> **方法论修正**：后续任何 DAG 收益评估，应输出**弹性**（移除边后的关键路径差），而不是批间方差。方差大只说明"值得去看依赖图"，不说明"值得做流水"。

### 4.9 验证单元清单（Verification-unit Inventory）与 MVWU 雏形

评审提出"验证单元清单可能比 11/34 更重要"——**采纳，且数据已可测**。按验证层次盘点两个项目：

| 层次 | 定义 | agateon | PeekView |
|------|------|---------|----------|
| **L0 切片级**（批自带测试，批完成即验证） | 批内单测/静态检查，批 commit 时运行 | **实践已存在但未制度化**（见下） | 2/63 任务（`T075`、`TPV0095` 有 `P5_backend`/`P5_frontend`/`P5_mcp`） |
| L1 阶段级 | P3 TDD 红 / P4 review | 全任务 | 全任务 |
| L2 任务级全量 | P5 全量套件 + consistency | 5/5 可核验任务 | 63/63（`make test-quick` = 全量后端 1068 tests） |
| L3 全局 | P6.5 judge（fresh context 全 BDD） | 全任务强制 | 同 |

**L0 的关键发现——MVWU 的雏形已经存在于既有实践**：

批级 commit message **已系统性携带批级测试证据**（实测 **25 条**）：

```
wf(TAG0034-P4): P4c 批 —— tmux 观测层（…pytest -k tag0034 = 90/0 全绿）
wf(TAG0034-P4): P4a 批 —— 配置路由核心…（57 绿 / 3 批次边界红）
wf(TAG0033-P4): 实现 CodexAdapter（19 红灯清零…）
```

**含义**：`batch` 已经是事实上的**最小可验证工作单元（MVWU, Minimum Verifiable Work Unit）雏形**——批有自己的测试、自己的测试运行、自己的证据。缺的不是新机制，而是三件**制度化**工作：
1. **证据位置**：批级测试结果现在散落在 commit message 散文里 → 应有标准落点（如 `P4-evidence/{batch}.log`）
2. **消费方**：没有任何 gate 校验批级证据 → L0 验证目前**纯自律**
3. **批→测试映射声明**：`pytest -k tag0034` 这类过滤器是 ad hoc 的 → 应在 `dispatch_plan.batches[]` 声明（如 `tests_filter:`）

**这改变了路径优先级的论证**：评审建议的"局部验证单元"（评审§21）**不需要等 DAG**——它是把既有实践制度化，零 schema 改动，且它才是让未来任何流水线有意义的前置条件（§4.5 的天花板 2 将随"切片级验证单元"的出现而自然松动）。

## 5. 可行性分析：阶段集与编排图的硬编码面

### 5.1 已数据驱动的部分（好消息）

`agate/rules/phases.yaml` **已经是声明式阶段图**：

```yaml
phases:
  - id: P0
    name: 任务简报
    exec_role: main-agent
    outputs: [{file: P0-brief.md, required: true}]
    gates: [{check: "..."}]
    retry_cap: 3
    next: P1
    retreat: null
    gate_pass_exit: 2
```

且 `agate-next.py` **消费**它做推进决策：
```
读 phases.yaml 当前 phase 的 gate_pass_exit（pass_set）+ next/retreat
→ 子进程跑 check-gate.py {phase}
→ exit ∈ pass_set → 查 next 推进
→ exit 1 → 查 retreat 回退
```

**这意味着"阶段关系"层已经是数据驱动的**（`next`/`retreat` 可表达任意图，不只是线性链）。这是 DAG 化的既有地基。

**但必须区分"关系"与"语义"两个层次**：

| 层次 | 载体 | 是否数据驱动 |
|------|------|-------------|
| 阶段**关系**（谁接谁、回退到哪、通过码） | `phases.yaml` 的 `next` / `retreat` / `gate_pass_exit` / `retry_cap` | ✅ 是——`agate-next.py` 机械消费 |
| 阶段**产出声明**（该阶段产出哪些文件、是否必需） | `phases.yaml` 的 `outputs` | ✅ 是（部分被消费） |
| 阶段**语义**（怎么判定合格） | `phases.yaml` 的 `gates` 字段 + `check-gate.py` 的 `gate_pN()` | ❌ **否**——`gates` 字段是**散文描述**，仅被 `check-structure-consistency.py` 用于 YAML↔md 对齐校验；**真实判定逻辑在手写的 10 个 `gate_pN()` 函数里** |

核验：
```bash
# gates 字段的消费方（仅结构一致性，非判定）
$ grep -rn 'phase.get("gates"' agate/scripts/*.py
agate/scripts/agate-next-card.py:133          # 卡片渲染
agate/scripts/check-structure-consistency.py:384,386  # YAML↔md 对齐
# 真实判定：check-gate.py 的 handlers 字典 + 10 个 gate_pN() 函数
```

**含义**：新增一个阶段，`phases.yaml` 加一条记录**只能让"关系"生效**；要让 gate 真正工作，**必须写一个新的 `gate_pN()` 函数并注册进 `handlers`**——这是 §5.2 里最重的一项成本，也是"阶段集可扩展"离"声明式即插即用"最远的一段距离。

### 5.2 烘焙面清单（成本所在）

|----|------|------|---------|

### 5.3 非数字阶段名（`p-alpha`）的破坏点（重点）

用户设想中的 `p-a` / `p-alpha` 会直接命中**三处**静默失效（前两处同一 `[0-9]+` 模式，第三处为 `P[0-8]` 模式）：

```python
# check-gate.py:1465-1466  回退抵达检测
old_num = re.search(r"[0-9]+", old_phase)   # "p-alpha" → None
new_num = re.search(r"[0-9]+", phase)       # "p-alpha" → None
if old_num and new_num and int(old_num.group(0)) > int(new_num.group(0)):
    # None 时短路 → 回退检测恒不触发（静默失效，不报错）
```

```python
# check-state-transition.py:212-214
def phase_num(text):
    m = re.search(r"[0-9]+", text)
    return int(m.group(0)) if m else 0      # 所有非数字阶段 → 0
```

```python
# pre-commit-gate.py:82 + 192-194（第三处，hook 主入口）
_P_NUM_RE = re.compile(r"P[0-8]")           # ← 注意：不是 [0-9]+，而是 P[0-8]
def _phase_num(phase_text):
    m = _P_NUM_RE.search(phase_text or "")  # 无匹配返回 None（非 0）
# 调用点 L291/L576：if not out_phase: continue  → 静默跳过
```

**第三处与前两处的差别（独立评审修正）**：前两处用 `re.search(r"[0-9]+", ...)`（提取数字，无匹配回退 0/短路）；第三处用 `P[0-8]`（**大小写敏感**，连 `p4` 都不匹配，无匹配返回 `None`）。**失效机制不同但后果同类**——非数字阶段名会被静默跳过，且该文件是每个 commit 都跑的 hook 主入口。

**危害等级：高**——不是"报错"，而是**静默地不检测**。回退声明会让 gate 跳过完成度校验（`check-gate.py` 回退分支直接 `exit 2`），非数字阶段名会让这个保护**完全失效**；且 `pre-commit-gate.py` 是**每个 commit 都跑**的入口，失效面覆盖全部提交流程。

**另需注意**：`check-gate.py` 对未知阶段直接 `exit 2`（视为通过）——

```python
func = handlers.get(phase)
if func is None:
    sys.stderr.write(f"未知阶段: {phase}\n")
    sys.exit(2)      # ← exit 2 = 多数阶段的"通过"码
```

**这意味着：新增一个阶段却忘记注册 gate 函数，gate 会静默"通过"而非报错。** 这是一个**fail-open** 设计——与 agateon 其他地方的 fail-closed 取向（如 DSH preset 挂载失败拒绝建会话）相反，值得单列为风险（R11）。

### 5.4 自定义阶段（`p-alpha`）的完整落地路径

若要支持用户自定义阶段，按依赖顺序需要：

| 步 | 动作 | 依赖 | 风险 |
|---|------|------|------|
| 1 | `phases.schema.json`：`enum` → `pattern`，并放开 `additionalProperties` 以容纳 `order`/`predecessors` | — | 低 |
| 2 | `phases.yaml` 每阶段加**显式序**（`order: 10` 或 `predecessors: [P1]`） | 1 | 低 |
| 3 | 替换三处 `re.search(r"[0-9]+")` 为查表（`check-gate.py` / `check-state-transition.py` / `pre-commit-gate.py`） | 2 | **中**——行为等价性需回归 |
| 4 | gate 注册改为**fail-closed**（未知阶段 → exit 1 而非 2）+ 提供默认 gate 或强制声明 | 1 | 中 |
| 5 | `MAX_RETRY_MAP` 字符串 → YAML 驱动（已有 `retry_cap` 字段，需打通） | 2 | 低 |
| 6 | `state-machine.md` 27 行转移表 + `WORKFLOW.md` 总览表与 YAML 同步（现有 S-1/S-2 结构一致性检查可复用） | 2 | 低 |
| 7 | 新增阶段卡片 + 角色文件（若新阶段用新角色） | — | 中（人工产出） |
| 8 | 130 个测试文件的阶段假设核查 | 3 | 中 |

**关键先例——协议已支持"自定义角色"扩展**（`agate/assets/templates/custom-role.md`）：

```markdown
---
role_id: {唯一标识，如 db-migration-specialist}   # ← 自由填写，非 enum
type: {execution | review}
phases: [{适用阶段，如 P2, P4}]                   # ← 角色声明自己适用于哪些阶段
---
```

**这说明**：
- 协议**已有"用户自定义扩展"的成熟范式**——角色可自定义、可声明适用阶段，且模板注释明确"复制本模板，按需填写，放到 execution-roles/ 或 review-roles/ 下"
- **角色与阶段的关系是"角色声明适用阶段"**（`phases: [P2, P4]`），而非"阶段硬编码角色清单"——这是**数据驱动的方向**
- 对照之下，**阶段本身**目前是 enum 硬锁 + 10 个手写 gate 函数——**阶段扩展的机制成熟度显著低于角色扩展**

**推论**：若要支持自定义阶段，**最自然的路径是复用角色的既有范式**——
1. 阶段用**声明文件**（类似 `custom-role.md` 的模板机制）而非 schema enum
2. 阶段声明自己的**产出 / gate 类型 / 适用角色**，gate 用**声明式类型**（如"文件存在型""测试通过型""命令 exit 0 型"）而非 10 个手写函数
3. 这与 `dispatch-tiers.yaml` 的"档位词表 + 绑定分离"设计同构——**协议层定义类型，项目层声明实例**

**这大幅降低了 §5.4 的成本预期**：不需要发明新机制，而是**把角色扩展的既有范式迁移到阶段层**。但前提仍是 §5.3 的显式阶段序（数字假设必须先解掉）。

**结论**：**步骤 1–3 + 4（fail-closed 修复）是"阶段集可扩展"的最小可行集**，且**不改任何现有阶段的行为**（P0-P8 全部保留，只是不再靠数字序推导顺序）。步骤 5–8 可增量跟进。

**与 DAG 的关系**：**阶段集扩展不依赖 DAG**，DAG 也不依赖阶段集扩展——两者是**正交议题**。但两者共享同一处地基（步骤 2–3 的显式阶段序），所以**先做地基对两者都有利**。

## 6. 维度分析

### 6.1 状态表示

| 现状 | DAG 所需 |
|------|---------|
| `.state.yaml` 单标量 `phase:` | 向量/矩阵：`tracks: {a: P4, b: P3}` 或 `phase: {a: P4, b: P3}` |

**连带影响**：
- `check-state-yaml.py` / `agate-state-get.py` / `agate-state-yaml-check.py` 全部按标量解析
- hook 的 `pre-commit-gate.py` 读当前 phase 决定跑哪个 gate
- 多值 phase 下，"本次 commit 属于哪个 phase"需要显式声明（每 commit 带 track id）
- **向后兼容**：存量 34 个任务的 `.state.yaml` 是标量，需兼容层（标量 = 单 track 特例）

### 6.2 Gate 语义

| 现状 | DAG 所需 |
|------|---------|
| `check-gate.py P4 {task_dir}` 校验**整份**阶段产出 | per-track gate：`check-gate.py P4 --track a` |
| 通过码 `gate_pass_exit` 按阶段定义 | 需按「阶段 × track」聚合：全体通过才算屏障通过 |

**核心矛盾**：phase gate 的语义是"整份交付物合格"。切片化后：
- 若 gate **仍按整份**校验 → 切片无法独立推进（等于没变）
- 若 gate **按切片**校验 → **跨切片集成缺陷的拦截点消失**

**缓解设计**：保留一层"merge gate"（跨切片一致性 + 集成测试），把"整体合格"的保证从"每阶段"挪到"每个 merge 点"。但 merge 点的定义本身是新协议面。

### 6.3 产出文件与合并

| 现状 | DAG 所需 |
|------|---------|
| `P4-implementation.md` 单文件 | 切片分片 `P4-implementation-a.md` + 合并产物 + 冲突语义 |

**已有先例可复用**：P8 已经是"多包拆批 → 各写 `P8-release-{pkg}.md` → 合并 subagent 整合唯一 `P8-release.md`"（`dispatch-protocol.md` 全阶段适用表 P8 行）。**这套"分片 + 合并 subagent"模式可以推广到 P3-P5**——这是 DAG 化成本最低的一块，因为模式已验证。

**共享文件冲突**：现有「并行规则」第 3 条已规定"跨批共享文件由主 Agent 在所有 subagent 返回后统一处理"。切片流水下，这个"统一处理"时点从"阶段末"变成"merge 点"——语义一致，只是触发时机变化。

### 6.4 调度与资源

用户设想中的"释放 sub 后的资源可再并发点什么"= **工作保持调度（work-conserving）**。

| 维度 | 现状 | 评估 |
|------|------|------|
| 并发上限 | `parallel_limit` 默认 3，可覆盖（实测有 8） | 已有弹性 |
| 上限依据 | "平台并发 + **主 Agent 上下文承载上限**" | **真正的约束是主 Agent 上下文** |
| 切片释放后复用 | 无显式机制 | 属主 Agent 调度纪律，**不需要协议改动** |
| 跨任务并行 | **未落地**（`loop-orchestration.md`：需独立 `.state.yaml` + worktree 隔离；hook 已支持多任务） | 独立议题，见 §8 路径 C |

**关键约束**：切片数 k 增加会**线性增加主 Agent 的协调负载**（每切片每阶段一次派发 + 一次汇总）。`parallel_limit=3` 的设计理由明确写了"主 Agent 上下文承载上限"——**DAG 化的并发度上限受此约束，不随愿望提高**。

**更硬的量化约束**（`dispatch-protocol.md` 工作量评估表）：

| 维度 | low | medium | high |
|------|-----|--------|------|
| 产出规模 | **≤3 个文件，单文件 ≤500 行** | 4–6 文件，或单文件 500–1500 行 | >6 文件，或单文件 >1500 行 |

- 包级并行**不改变**拆分原则的其他条目：**产出文件数/输入文件数限制仍适用于每个并行 subagent**（`dispatch-protocol.md:687`）
- 即：DAG 切片化后，每个切片仍须满足 ≤3 文件 / ≤500 行的粒度约束 → **切片不能无限细化**，存在下界
- 主 Agent 上下文另有实证教训：空返回的根因是"认知过载"而非窗口占满（`:138`）——**切片数增加会加剧协调侧的认知负载**，这正是 DAG 化的隐性成本

#### 6.4.1 与既有 6 条局限的交互（`LIMITATIONS.md`）

| 局限 | 与 DAG 化的关系 |
|------|----------------|
| 1. gate 可信度取决于测试质量 | 中性——DAG 不改变测试质量，但切片化可能**降低集成测试覆盖**（各切片自测通过 ≠ 集成通过） |
| 2. 角色隔离是认知层面的隔离 | 中性 |
| 3. **主 Agent 判断力是单点故障** | **放大**——切片调度、merge 时点、失效传播判断全部压在主 Agent 上 |
| 4. subagent 中间过程不可观测 | **放大**——并发切片越多，可观测性缺口越大；当前已有"卡死检测"（RM-AG0055）但仍受限 |
| 5. gate/hook 依赖 python3+git+pyyaml | 中性 |
| 6. vision/UI 验收依赖外部设施 | 中性（但 UI 类任务的切片化收益更依赖该设施） |

**结论**：DAG 化**放大局限 3 和 4**——两条都是"主 Agent 是瓶颈/盲区"类局限，与 §6.4 的上下文约束同源。这是 DAG 化必须正视的结构性代价：**它把并行度收益的一部分，换成了主 Agent 的认知负载与观测盲区**。

### 6.5 质量保证与失效传播

**这是 DAG 化最大的代价**：

| 风险 | 机制 | 后果 |
|------|------|------|
| **失效传播** | 切片 A 在 P4 发现接口设计错误 | 切片 B/C 的 P5 验证全部作废，需跨 track 回退 |
| **屏障价值削弱** | 现状在 P2/P5 拦截跨切片缺陷 | 流水线把拦截点后移到 merge 点，**发现更晚、返工更大** |
| **judge 无法并行化** | P6.5 强制 fresh context 重验**全部** BDD（跨切片端到端） | **尾部 P6/P6.5/P7 永远是硬屏障**——流水线只能压缩中段 P3-P5 |

**收益天花板**：即使中段完全流水化，尾部三个阶段的屏障仍在。以实测中位数为参照（P3 101 + P4 19 + P5 10 = 130 分 vs P6 20 + P6.5 ? + P7 7），**中段占大头**，所以压缩中段仍有意义——但"P0 到 P8 全流水"是不成立的。

### 6.6 可追溯性与审计

| 现状 | DAG 所需 |
|------|---------|
| `gate-events.jsonl` 哈希链，事件含 phase | 事件需含 track id；哈希链语义扩展 |
| `trace_id: {Txxx}-{Pn}-{YYYYMMDD}` | 需 `{Txxx}-{Pn}-{track}-{date}` |
| 每阶段一 commit，阶段=原子进度单位 | 每 track 每阶段一 commit + merge commit |
| `check-events.py` 校验事件链完整性 | 需支持 track 维度 |

**成本中等，但风险在于**：审计链是 agateon 可验证性的基础（DAG 化不能牺牲它，否则 gate 的机械性失去依据）。

**哈希链的线性性质是 DAG 的结构性障碍**（`check-events.py:9-10`）：

```
3. 首行 prev_hash == GENESIS_HASH（不符 → exit 1）
4. 逐行 prev_hash == sha256(上一行原始文本 UTF-8)（链断裂 → exit 1 = 历史行被改写检测）
```

- **链是严格单线性的**：每行绑定**前一行原文**——并发 track 若各自 append，会**破坏链**（两条并行写入都指向同一前驱）
- **解法只有两类**：
  1. **串行化写入**：所有 track 的事件仍由单点（主 Agent / hook）串行 append——**这消除了写入并行性**，但保留了事件可并行产生的语义
  2. **多链/分叉链**：每 track 一条哈希链 + 合并点记录——需重新设计 `check-events.py` 的校验算法（从"单链"变"链森林 + 合并事件"）
- **另有已知盲区**：`check-events.py:20` 自述「删除尾部无法由哈希链检测」——DAG 化的多 writer 场景会**放大**这个盲区

**评估**：审计链**不是不可扩展**，但两条解法各有代价（1 牺牲写并行、2 增加算法复杂度）。这是 §7.3 成本估算中容易被低估的一块。

**另注**：`check-events.py:14`「**未知 event 类型不拦截**（向后兼容）」——这是**fail-open** 设计，与 §5.3 的 gate fail-open 同源。DAG 若引入新事件类型（如 `track_start` / `merge_point`），**旧版本校验器会静默放过而非报错**——跨版本兼容性上这是优点，但**新机制上线时缺少"校验器不认识新事件"的告警**，属于需注意的盲区。

### 6.7 人机协作

实测显示长间隔占 73.8%。DAG 化对人机界面的影响：

- **正向**：切片释放后可立即派下一批，减少"等最慢切片"的空转
- **负向**：主 Agent 需要更频繁的人类介入点（merge 冲突、接口变更决策），**可能增加而非减少人工等待**
- **关键**：如果 73.8% 的耗时真是人工等待，那么**并行更多工作不会缩短等待**，只会让等待期间"有更多东西在跑"——这提升吞吐，但**不缩短单个任务的交付时间**

### 7.1 失败恢复（PAUSED）在 DAG 下的复杂度

现状：`state-machine.md` 有 **56 处提及 PAUSED**，状态集合为
`{P0…P8, READY, DONE, PAUSED}`，触发条件包括 `NEED_CONFIRM` 阻塞、`status: GAP`、
`PROD_TOUCHED`、不可逆操作等，且明确"正确路由：上游问题需人工介入，非 agent 失败"。

DAG 下的新增问题：

| 问题 | 说明 |
|------|------|
| 部分暂停 | 切片 A 触发 PAUSED 时，切片 B/C 是继续跑还是全体停？现状状态机是**任务级**单一状态，无"部分暂停"表达 |
| 恢复语义 | 恢复时哪些切片需要重跑？若要作废 B/C 的下游工作，需跨 track 失效传播 |
| 人工介入点倍增 | 每个 merge 点都可能需要人工裁决接口变更 → **可能增加而非减少人工等待**（与 §6.7 呼应） |

**结论**：PAUSED 是任务级概念，DAG 需要**track 级暂停 + 跨 track 失效**语义。这是现有状态机之外的新协议面，成本未被 §5.2 计入。

### 7.2 平台差异

现状（`platform-notes.md`）：
- `~/.agate` 软链 / 版本目录在 Linux/macOS/Windows 均有适配，Windows 无符号链接权限时**退化为复制模式**（`AGATE_HOOK_COPY_MODE=1`）
- 升级后需重跑 `install-hook.py`（复制不自动跟随源文件）
- CI backstop 原生支持 GitHub Actions / GitLab CI / Gitea Actions

对 DAG 化的影响：
- **状态文件的并行写入**：多 track 若各自写 `.state.yaml`，在 Windows 复制模式 + 文件锁语义差异下风险更高（现状是单写者，冲突面小）
- **worktree 依赖**：路径 B/C（任务级拆分、跨任务并行）依赖 worktree 隔离；Windows 上 dogfooding 流程的软链语义已被验证有退化路径，需确认 worktree 并发下的行为
- **hook 复制模式**：DAG 若新增 hook 逻辑，Windows 需额外验证"复制模式下 hook 与协议版本不一致"的场景

**评估**：平台差异不构成阻断，但**新增了 Windows 侧的验证矩阵**（现有 130 个平台的测试文件已按 `windows_smoke` 分层，新机制需跟进）。

### 7.4 自定义阶段的治理边界（协议本体 vs 项目数据）

现状边界清晰：
- `agate/rules/phases.yaml` = **协议本体**，改动触发 SELF-GATE（需独立评审）
- `agate-workspace/` = 项目数据，不受 SELF-GATE 治理

若"阶段集可扩展"落到"用户可定义 `p-a`/`p-alpha`"，则产生一个**边界问题**：

| 情形 | 问题 |
|------|------|
| 用户改 `phases.yaml` 加阶段 | 触发 SELF-GATE → 用户改自己的阶段却要走协议评审，体验不合理 |
| 阶段定义移出协议本体 | 则"协议本体"不再自包含，`check-structure-consistency.py` 的 YAML↔md 对齐锚点失效（S-1/S-2 以 `phases.yaml` 为 YAML 侧锚点） |
| 项目级阶段覆盖协议阶段 | 需新增"协议默认 + 项目覆盖"的两层合并语义（类似 `dispatch-routing.yaml` 的 tier_bindings 分层，该模式已有先例可借鉴） |

**建议方向**（供后续设计参考）：沿用 `dispatch-routing.yaml` 已验证的**分层模式**——协议层定义**阶段语义模板**（如"验证类阶段"的通用 gate 骨架），项目层声明**阶段实例与顺序**（不受 SELF-GATE）。但这需要先解决 §5.3 的 fail-open（否则项目层加阶段无 gate 会静默通过）。

**风险等级中高**：这不是"加个字段"的问题，而是**协议本体与项目数据的重新划界**——属于设计层决策，需人工判断（见 §9.3 未决问题 1）。


### 7.5 破坏性变更与迁移成本（DAG 特有的额外负担）

DAG 化必然改动 `.state.yaml` 的 `phase` 语义（标量 → 向量），而**这在 agateon 的版本治理里被明确定义为破坏性变更**。

**先例**（`agate/UPGRADING.md` 已知破坏性变更章节）：

| 版本 | 变更 | 影响面 | 迁移动作 |
|------|------|--------|---------|
| v0.40.0 | `task_id` 格式硬切（`T\d+` → `T[A-Z]{2}\d+`） | **进行中任务 + 已部署项目** | 改 `.state.yaml` 编号；orchestrator 从拷贝改符号链接；项目特定约束迁至 `project.md` |
| v0.43.0 | 工作区子目录 8→9 | 进行中任务 + 已部署项目 | 目录迁移 |
| v0.41.0 | `docs/tasks` → `agate-workspace/` | **所有已部署项目 + 进行中任务** | 目录迁移 |

**DAG 化的迁移负担**：

| 项 | 内容 |
|----|------|
| 存量任务 | 34 个任务的 `.state.yaml` 是**标量 phase**，需兼容层或迁移 |
| 下游项目 | 协议使用者（如 PeekView）的进行中任务同样受影响 |
| 迁移工具 | 有范式可循（`agate-migrate-workspace.py` 是既有迁移脚本） |
| 版本语义 | 需在 `UPGRADING.md` 新增章节 + 破坏性变更说明（现有流程要求"无破坏性变更也写"） |
| 兼容策略 | 报告 §6.1 已建议"标量 = 单 track 特例"的兼容层——**这是把破坏性变更降为兼容性扩展的关键**，但需验证钩子/脚本全部走兼容路径 |

**评估**：破坏性变更本身**可管理**（有先例、有迁移工具范式、有兼容层设计），但它**叠加在协议内核改造之上**，进一步抬高了路径 A 的总成本。这也是 §8 路径 B（任务级拆分，**零 schema 变更**）优势的又一来源。

## 8. 增量路径对比

| 路径 | 内容 | 收益 | 成本 | 前置 |
|------|------|------|------|------|
| **A. 真 DAG** | phase 向量 + per-track gate + merge 协议 | 理论上限 | **协议内核重写**（§5.2 + §6 全部） | §5.3 阶段序显式化 |
| **B. 任务级拆分 + 集成任务** | 把 front/back/db 拆成**独立任务**各自跑 P0-P8，加一个集成任务/接口冻结产物 | **接近 A 的并行收益** | **低**——复用现有状态机、gate、worktree、看板 | 接口冻结纪律 |
| **C. 工作保持调度** | 子任务完成即复用槽位；跨任务并行（需 worktree 隔离） | 提升吞吐、填补人工等待 | **极低**——主 Agent 调度纪律 + 已有 worktree 基础 | 无 |

**B 与 A 的关系（重要）**：A 最贵的部分（phase 向量、per-track gate、审计扩展、破坏性变更迁移）**正是 B 绕开的部分**。两者的收益来源相同（并行独立切片）。若 P2 真的冻结了切片间接口，切片就可以成为**独立任务**——**B 是 A 的廉价等价物**。

**结合 §4.6 的修正**：既然 A 的**可实现收益池仅 11/34 且被三重天花板压缩**，而 B 能以近零成本捕获同等收益，则：
- **A 的性价比进一步恶化**——高成本（协议内核 + 破坏性变更）× 小收益池
- **A 唯一可能不可替代的场景**收窄为：切片间**共享大量实现状态**（无法独立成任务）、**且**存在显著跨阶段耗时异构、**且**其验证可切片。三个条件同时满足的场景在现有 34 任务样本中**未被观察到**。

### 9.1 结论

### 9.3 未决问题（需人工判断）

1. **"阶段"的本质是什么？** 当前 P0-P8 是软件工程 workflow 的固化。若阶段集真的可扩展（`p-alpha` 等），那么"阶段"是**用户可定义的编排单元**，`phases.yaml` 需要成为用户可写文件——这涉及协议本体与项目数据的边界（当前 `agate/rules/` 是协议本体、SELF-GATE 治理）。
2. **人机等待是否可通过并行消除？** 若 73.8% 是人工决策等待，并行只能提升吞吐、不能缩短交付时间。这需要产品层面的判断（用户要的是"单任务更快"还是"同时推进更多"）。
3. **DAG 化的边界条件如何机械校验？** "切片间真正独立"是语义判断。**协议已有可借鉴的半机械范式**——`coupling_checklist`（`state-machine.md:197-211`）：
   - **机械部分**：`check-pruning.py:185-196` 机械校验字段存在性（裁剪 P7 必须有 `coupling_checklist: [...]`，且不得声明 `implicit_coupling`）
   - **非机械部分**：清单**内容**（如 `api-schema: checked, data-model: checked`）靠 **self-declaration nudge**——协议自述"可以无脑填，但强制写一行制造'我考虑过风险'的形式义务"
   
   **推论**：切片独立性可以复用同一范式——机械校验"是否声明了切片边界 + 是否列出检查过的耦合点"，把实质判断留给 P2 architect（并在 P7 由 consistency-reviewer 交叉验证）。**这降低了未决问题 3 的难度**：不是"无法机械校验"，而是"只能机械校验形式、不能校验实质"，而这**已是 agateon 既有的设计取向**。
4. **收益池会随任务复杂度增长吗？**（v2 新增）多包任务占比的历史趋势**在上升**：早期（TAG0001–0014）71% → 中期（0015–0027）54% → 近期（0028+）**86%**。若任务持续变大、批次持续增多，§4.6 的"收益池仅 32%"可能**随时间变化**。但注意：§4.5 的天花板 2（P5 全量验证）是**机制性**的，**不会**随任务变大而消失——除非同时引入"切片级验证 + 最终全量验证"的两级设计。
5. **是否为"未来的大任务"预付成本？** 路径 A 是协议内核级改造（§7.3）。若收益池当前小但趋势上升，可选择"**等收益池变大再做**"或"**先做地基（阶段序显式化）保值**"——后者是 §9.2 建议 2 的另一种论证。

## 10. 架构演进方向（v4 新增——综合外部评审）

### 10.1 两张图，不要混成一张

现状：`phase` 同时承担四种职责——workflow 语义、执行排序、**验证边界**、状态权威。单任务时代这是优点（简单、可机械校验）；规模化后它把两件本质不同的事耦合在一起：

| 图 | 回答的问题 | 节点 | 边 |
|----|----------|------|----|
| **Task Graph**（执行图） | 什么工作可以并行？ | 任务/切片 | 依赖（文件/接口） |
| **Verification Graph**（验证图） | 什么证据必须经过什么验证？ | 产物/证据 | 验证规则（局部测试 → 集成 → 全量 → judge） |

**评审的判断（采纳）**：这两张图应当**逐渐正交**——Task Graph 决定调度，Verification Graph 决定放行。§4.9 的 MVWU 正是连接点：**每个 MVWU 自带它的 Verification Graph 子图**（批级测试 → 集成 → 全量 → judge）。

### 10.2 MVWU 作为下一阶段的核心抽象

> **MVWU（Minimum Verifiable Work Unit）**= 最小的"自带验证证据"的工作单元。

定义一旦成立，此前分散的议题会**突然统一**：

| 议题 | 在 MVWU 语义下的形态 |
|------|---------------------|
| 任务级拆分（路径 B） | 把 MVWU 组装成独立任务 |
| 工作保持调度（路径 C） | MVWU 完成即释放槽位 |
| 局部验证（§4.9） | MVWU 自带的 L0 验证 |
| 真 DAG | MVWU 之间的依赖图调度 |
| 风险治理 | 按 MVWU 的风险等级选验证深度 |

且 **§4.9 已证明其雏形存在于既有实践**（批级 commit 携带批级测试证据）——MVWU 是**制度化**，不是**发明**。

### 10.3 遥测：缺口比设想的小

评审建议的活动遥测（`dispatch_started/finished`、`agent_active/idle`、`human_wait`…）对照现状：

| 评审提议 | 现状 | 缺口 |
|---------|------|------|
| gate 耗时 | **已有**——`gate_run` 事件带时间戳（111 条） | 无 |
| 派发决策 | **已有**——`dispatch_route` 事件（TAG0034） | 无 |
| 派发起止 | 部分——`dispatch_route` 记决策不记起止 | 补 1–2 类事件 |
| agent 活跃/空闲 | **已有数据源**——RM-AG0055 命令流日志（本会话实测：5 秒诊断出 FROZEN） | 需把 detect 结果**周期性写入 ledger** |
| 人工等待 | 无信号 | 需定义（如"transition 后无事件且无 dispatch"区间） |

**结论**：遥测是 **P0 里成本最低的一项**——大半管道已存在，缺的是接线，不是新机制。

### 10.4 战略定位：Verification Plane（引用评审§24，采纳）

> Control Plane（路由/fleet/预算）是产品功能——OpenHands、Codex、Devin 都在做，终将商品化。
> **Verification Plane（证据 → 独立验证 → 可信状态 → 发布）才是 agateon 的 protocol moat。**

这与本报告的机制发现同构：agateon 的差异化资产正是**机械可校验的门禁与审计链**（哪怕 §6.6 指出其扩展成本）。任何编排演进（DAG/流水）都不得以削弱 Verification Plane 为代价——这也是 §6.5"并行独立验证、绝不并行验证与被验证物"红线的战略表述。

### 10.5 反事实模拟的边界

评审建议的四策略模拟（Current / Work-conserving / Task split / True DAG）**暂不可完整执行**：它依赖 §10.3 的遥测（尤其"agent 活跃 vs 人工等待"切分）。可先给出的**有界结论**（基于已重建的批级时间线）：

| 任务 | Current | Work-conserving | True DAG（移除屏障） |
|------|---------|-----------------|---------------------|
| TAG0034 | P4 链 442 min | **+0**（单链无可并行） | **+0**（依赖真实存在） |
| TAG0033 | 两批串行 63 min | ≈+15~25 min（批间重叠） | **+0**（P5 全量屏障不动） |

两个可重建样本都指向同一结论——**与 §4.6/§4.8 一致**。完整模拟等遥测落地后进行。

## 11. MVWU：从"野生形态"到协议最小集（v5 新增）

第二轮评审主张"v4 无意中逼出了 Agateon 下一代核心数据模型 MVWU"，并把 MVWU 定义收紧为：

> **MVWU = 具有明确输入边界、产出边界、验证契约与 provenance 的最小工作单元，且完成状态可机械验证。**

**本报告接受这个方向，但用证据给出比评审更强的结论**：MVWU 的四个不变量**不是待建的新机制**——它们**几乎全部已有机械锚点**。

### 11.1 四不变量的既有锚点（实证）

| 不变量 | 评审定义 | **既有锚点（实证）** | 成熟度 |
|--------|---------|-------------------|--------|
| **I1 Boundary** | 能明确知道它改了什么 | **批级 commit 的文件集**（git 原生，可机械还原） | 实证可用，**未结构化声明** |
| **I2 Verification** | 能明确知道什么证明它正确 | **批自带测试文件 + 批自带证据文件 + 批级测试结果** | 部分结构化 |
| **I3 Provenance** | 能明确知道证据对应哪个工作结果 | **`check-p6-provenance.py` 七道客观审计**（证据-结论对应 / BDD 总数对照 / 日志 EXIT_CODE 一致性 / P5 证据复用校验…） | **成熟**（任务级） |
| **I4 Composability** | 多个 MVWU 可组合成更大 task | **任务级拆分实践**（`dispatch-protocol`："写不出一句话 → 任务太大，考虑拆分"）+ 本报告 §8 路径 B | 实践存在 |

**I1/I2 的实证**（`TAG0034` P4c 批，commit `92edcfc`）：

```

 agate/tests/unit/test_tag0034_p4c.py          | 221 +++++   ← 批自带测试
 agate/scripts/agate_dispatch_route.py         | 201 +++++   ← 批产出
 .../P4-implementation-P4c.md                  |  79 +++++   ← 批自带证据
 .../P4-dispatch-context-implementer-P4c.md    | 270 +++++   ← 批上下文
```

**批已经是事实上的 MVWU**：有自己的文件集（I1）、自己的测试与证据文件（I2）、任务级 provenance 覆盖（I3）、可组合成任务（I4）。**它缺的不是机制，是"把事实写成声明"。**

### 11.2 最小改动集（零协议内核改动）

| # | 改动 | 锚点 | 成本 |
|---|------|------|------|
| 1 | `dispatch_plan.batches[]` 增可选 `tests_filter`（如 `pytest -k tag0034`）——把 ad hoc 过滤器**声明化** | I2 | 极低（schema 加可选字段） |
| 2 | 批级测试结果落**结构化位置**（如 `P4-evidence/{batch}.log`）而非 commit message 散文 | I2 | 低（约定 + 一条 check） |
| 3 | （可选）批级 gate：批完成时跑该批 `tests_filter`，非零即批未完成 | I1+I2 | 中（新增 gate 分支） |
| 4 | （可选）`files_expected` 声明 + 与 git 实际文件集比对 | I1 | 低 |

**关键**：1、2 两项即可让 L0 验证从「自律」变为「机制」（§4.9 的三项制度化工作中前两项），**且不触碰 `.state.yaml`、gate 语义、审计链、P6.5**——与 §8 路径 C 同级成本。

### 11.3 与既有机制的关系：不新建子系统

评审建议把 MVWU/Task Graph/Verification Graph/Evidence Contract/Provenance/Scheduler **六者边界一次定义清楚**（并写一份协议文档）。**本报告建议分两步，理由是基于 agateon 自身的演进路径**：

| 评审建议 | 本报告调整 | 理由 |
|---------|-----------|------|
| 先写《MVWU Protocol — Design & Invariants》 | **先做最小改动集的试点**（挑一个多批任务），**再用试点证据写协议** | agateon 自身的路径是 `practice → evidence → invariant → protocol`（评审§1 引用）；先写文档再落地，正是评审§22 警告的"新官僚主义"风险 |
| 六概念一次定义 | 先定义 MVWU（其余五者作为**视图**存在） | Task Graph / Verification Graph / Evidence Contract / Provenance / Scheduler 中，后四者**已有部分实体**（§11.1）；一次定义六个会固化未经验证的边界 |

### 11.4 反官僚化：字段预算是硬约束

评审 §22 的警告（"一个 bug 修复要填 30 个字段，Agateon 就死了"）**必须变成可执行的约束**，否则 MVWU 会重演本报告 §5.2 的硬编码膨胀：

| 规则 | 内容 |
|------|------|
| **最小默认** | 简单任务**零新增字段**——MVWU 声明为可选；未声明 = 沿用现状（batch 隐含单元） |
| **风险触发** | 仅高风险 / 多切片 / 跨端任务需要显式声明边界与验证契约 |
| **字段预算** | 显式声明 ≤5 个字段（`id` / `output` / `verify` / `risk?` / `deps?`）——超出即视为设计错误 |
| **可机械校验** | 每个字段必须有消费方（check 或 gate）；无消费方的字段不许加（本报告 §5.1 的教训：`gates` 字段沦为散文） |

### 11.5 度量修正：11/34 不是长期指标（采纳评审 §9-10）

评审指出 **11/34 会随 MVWU 落地而失效**（分母改变）——采纳。应改用：

$$E_{pipeline} = \frac{T_{barrier} - T_{optimal}}{T_{barrier}}$$

并按 **MVWU 级**（而非任务级）统计，按项目聚合。当某项目的 `E_pipeline` 超过阈值时，才触发 DAG 研究（评审 §8 的 **Research Trigger**，采纳）：

```
if MVWU-level E_pipeline > threshold:  investigate DAG
else:                                  do not implement DAG
```

**这修正了本报告 §4.6 的定位**：11/34 是**当前状态的快照**（有证据、可复现），但不是决策公式；决策公式是 MVWU 级弹性 + 阈值。

### 11.6 遥测不得成为权威（采纳评审 §13）

评审要求"不要让 telemetry 变成新的 authority"——**与 agateon 既有原则一致**（RM-AG0055：检测输出"定位证据 + 触发核查、**不自动判死**"）。本报告 §10.3 的遥测设计据此定界：

| 遥测 → 允许 | 遥测 → 禁止 |
|------------|------------|
| 调度输入（该派谁、还有无空闲槽位） | 直接判 phase 失败 |
| 调查触发器（FROZEN/SPIN → 核查） | 自动中止 / 改状态 |
| 统计与弹性计算 | 写入 gate 判定依据 |

**观测与正确性必须分离**——这是本报告 §6.5"并行独立验证"红线在遥测维度上的同一条原则。

### 11.7 I1 可归属性的量化实证（v6 新增——本轮评审驱动的发现）

第三轮评审要求"I1 从'有 output 字段'升级为'如何机械证明声明与事实一致'"。**在执行该要求时发现一个比预期更硬的结构性约束**：

对 **frontmatter 批数 ≥2 的全部 16 个任务**（同轴口径——v6 初稿误用分析 §4.6 的"11 个可并行候选池"，两轴不同源，已修正）做实测：

**三档可复现判据**（口径差异会显著改变数字，故并列）：

| 判据 | 严格度 | 逐批率 |
|------|-------|-------:|
| A. commit subject 含 `-P4a` 类子批后缀 | 最严（零歧义） | **6%**（1/16） |
| **B. 人工核验批↔commit 一一对应** | 中（**采用**） | **13%**（2/16） |
| C. P4 commit 数 ≥ 批数 | 最宽（会误判） | 38%（6/16） |

**另发现**：「批是否逐批 commit」**无稳定命名约定**——`TAG0016` 用 `-P4a`、`TAG0034` 用中文"P4a 批"、多数不做标记。故 I1 的机械校验**同时受 commit 粒度与命名约定缺失两个限制**。

| 形态 | 任务数 | 占比 | I1 可机械验证 |
|------|-------:|-----:|-------------|
| **逐批 commit**（`TAG0016` `-P4a/P4b/P4c` 后缀 / `TAG0034` 中文"P4a 批"） | **2** | **13%** | ✅ |
| **合并 commit**（`TAG0012` 8批→1 commit / `TAG0017`「5批并行」→1 / `TAG0023` 5批→1 / `TAG0007` 4批→1 / `TAG0027` B1+B2 合并 / `TAG0019` core+docs-sync 合并 / `TAG0030` 四 phase 单 commit 等——**均已逐一核验**） | **14** | **87%** | ❌ |

**结论**：

> **I1 Boundary 的机械化只对"逐批 commit"形态成立，实测仅覆盖 13% 的多批任务（2/16）。**

这**不是一个实现细节，而是与 §4.5「验证不可切片」同源的结构性约束**——两者都是同一个事实的两种表现：

| 表现 | 内容 |
|------|------|
| §4.5（验证维度） | P5 是全量套件 → 无切片级验证单元 |
| §11.7（归属维度） | 87% 的多批任务为合并提交 → 无切片级**边界归属** |

**一个反直觉的相关性**：唯一"批↔commit 干净一一对应"的样本 `TAG0034` **不在候选池内**（它因 `serial: true` 被排除）。即：**提交粒度与"声明可并行"负相关**——声明越并行，越倾向合并提交，边界越不可归属。这意味着 MVWU 最想服务的那些批，恰恰是边界最难归属的批。

**含义**：并行执行 ≠ 可独立验证，**也 ≠ 可独立归属**。任何试图让"工作单元"成为可机械验证的 primitive 的设计，都必须先解决**提交粒度**问题——而当前协议模式 3（并行 → 汇总统一 commit）与"逐单元可归属"存在**直接冲突**。

**这为 MVWU 协议设计提出了一个必须由用户裁决的取舍**（已写入该设计文档 §11 未决问题 6）：

| 选项 | 收益 | 代价 |
|------|------|------|
| A. 保持合并 commit | 保留模式 3 的原子性 | I1 只覆盖 13% 的多批任务（其余退化 UNKNOWN） |
| B. 并行模式改逐批 commit | I1 可覆盖多数批 | 失去统一 commit 的原子性 |

**这是真实的新决策点，不是已有答案的重述**——实测协议对该取舍**只有单边立场、从未讨论另一侧**：

```bash
$ grep -rn "统一 commit\|逐批 commit" agate/dispatch-protocol.md
agate/dispatch-protocol.md:618: | 模式 3 | **并行** | ... → 各自产出 → 主 Agent 汇总统一 commit |
```

即：协议**明确规定**了并行批汇总统一 commit，但**没有**任何条文讨论"逐批 commit 以换取可归属性"这一权衡——它的代价（原子性）与收益（I1 可验证）**都未被评估过**。

**本报告不自行裁决**——这正是"结论应由证据指向、取舍应由人决定"的边界。
