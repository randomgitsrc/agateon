## 1. 问题

`check-scope-resolved.py` 的 `SCOPE_PLUS_RE` 原为：

```python
re.compile(r"^\s*-?\s*\[SCOPE\+\]", re.MULTILINE)
```

只认「行首 + 可选短横线 + 可选空格」。**粗体 `**[SCOPE+]**`（TPV0099 P2-design.md:120 的真实写法）与引用块 `> [SCOPE+]` 均返回 False。**

后果不是「误报」，而是**静默早退**：

```python
if not scope_found:
    sys.stderr.write("GATE SKIP: ... 未检出 [SCOPE+] ...")
    sys.exit(0)          # ← exit 0，与「已校验且通过」在退出码上不可区分
```

`v0.77.0` 之前该分支**完全静默**；`v0.77.0` 起输出 `GATE SKIP`（RM-AG0077 子批 A），但**退出码语义未变**。

## 2. 关键约束：必须**双侧协同**

`RM-AG0077⑦` 已实测确认的教训：**只放宽 `SCOPE_PLUS_RE` 一侧会造成假红。**

理由：若某一任务的 `[SCOPE+]` 被放宽后**新检出**，却因 `SCOPE_RESOLVED` 用了包裹形态而查不到 → 该任务在 gate **由绿转红**，而它其实是合规的。

**⚠️ 载荷点更正（独立评审指出，我已实测确认）**：初版把理由写成「`SCOPE_RESOLVED_RE` **同样只认行首**」——**不准确**。
两侧的形态**本来就不同**：`SCOPE_PLUS_RE` 的缺口是**粗体/引用**包裹，而 `SCOPE_RESOLVED` 侧的真实载荷点是**反引号**
（`TAG0021` 的 `P1-requirements.md:231` 首字节实为 `` ` ``，旧正则命中 0、只补粗体+引用仍不命中）。

**存量实例（实测）**：`TAG0021-structured-layer`——`P2-design.md:379` 是粗体 `**[SCOPE+] 发现…**`（PLUS 侧新增命中），
其 `P1-requirements.md:231` 的 `SCOPE_RESOLVED` 用反引号包裹（旧正则 0 命中、新正则 1 命中）。**仅此一个任务实测命中该形态。**

⇒ 本次**同时**放宽两侧：PLUS 侧加粗体/引用，RESOLVED 侧在两者之上**另加反引号**
（放宽 resolved 只会**减少**阻断，方向安全）。**变异测试**：只补粗体+引用而不补反引号 → `sc_11` 转红，证明反引号是**必需**项而非冗余。

## 3. 刻意保留的保守边界（不是遗漏）

| 形态 | 判定 | 依据 |
|---|---|---|
| 裸 `[SCOPE+]`、`- [SCOPE+]` | **声明** → 触发 | 原有行为 |
| `**[SCOPE+]**`、`__[SCOPE+]__` | **声明** → 触发 | 本次新增（TPV0099 实际写法） |
| `> [SCOPE+]` | **声明** → 触发 | 本次新增 |
| 行中出现（`本节讨论 [SCOPE+] 的处置`） | **提及** → 不触发 | 实测：行内任意位置匹配会新增 **24 个任务转红**，绝大多数是散文提及 |
| 行首反引号 `` - `[SCOPE+]` `` | **提及** → 不触发 | **以引述/否定为主，但存在真声明反例**——见 §3.2。纳入会新增 **5 个任务转红** |
| 标题形态 `## N. [SCOPE+] …` | **不覆盖** | 语义混杂（容器标题 vs 声明标题），见 §3.1。纳入会新增 **4 个任务转红** |

**为何不给「声明 vs 提及」做语义判定**：本 hotfix 期间试过一版基于「否定词前置 + 反引号包裹」的启发式分类器，
它在全仓命中大量任务、**绝大多数是散文提及** ⇒ 判断类语义机械化会退化
（与 `design-claim-evidence-binding.md` v1/v2 两次失败的同一模式）。故判据停在**形态**层面：认行首，不猜语义。
> 按 A8「无法给出命令的声称应删除」：此处**不写具体命中数**——该数字取决于启发式的实现细节（正则写法一变就变），
> 不构成可复核的稳定声称。可复核的是上表的**形态分类**与转红数（均有实测命令）。

### 3.1 已知边界一：**标题形态**（`## 8. [SCOPE+] 声明`）不覆盖

存量的「标题形态」实测 **15 处 / 涉及 10 个任务**（紧判据：`#` 与 `[SCOPE+]` 之间只允许**
可选编号** `N.`；见下方可复核命令）。若把判据放宽成「**标题行内任意位置**含 `[SCOPE+]`」则为
**26 处 / 15 个任务**——多出的部分**含标题内的句中提及**，语义**混杂**：

```bash
# 紧判据（本文件采用）：15 处 / 10 个任务
# ⚠️ `[SCOPE\+]` 的 `+` 必须转义——不转义会被当量词，判据恒不命中（本文件初版即踩此坑）
python3 - <<'EOF'
import re,glob,os
SKIP=re.compile(r"dispatch-context|dispatch-prompt|progress")
CARD=re.compile(r"<!-- AGATE_CARD_START -->.*?<!-- AGATE_CARD_END -->",re.DOTALL)
rx=re.compile(r'^\s*#+\s*(?:\d+\.\s*)?\[SCOPE\+\]',re.M)
occ=0;tasks=set()
for f in sorted(glob.glob('agate-workspace/tasks/*/*.md')):
    if SKIP.search(os.path.basename(f)): continue
    t=CARD.sub('',open(f,encoding='utf-8',errors='replace').read().replace('\r\n','\n'))
    m=rx.findall(t)
    if m: occ+=len(m); tasks.add(f.split('/')[2])
print(occ,'处 /',len(tasks),'个任务')
EOF
```

| 形态 | 实例 | 实际语义 |
|---|---|---|
| `## 8. [SCOPE+] 声明` + 正文「无新增隐含需求」 | `TAG0012:402`、`TAG0014:302` | **容器标题**，正文是否定 ⇒ 匹配它会**假红** |
| `## [SCOPE+] 声明` + 正文「无。四批实现均严格按已批准范围执行」 | `TAG0023:49` | 同上 |
| `### [SCOPE+] 发现：BDD-10 豁免清单遗漏第 5 类边界文档` | `TAG0025:80` | **真声明**（正文是真实缺口描述） |

**决策：不覆盖标题形态。** 理由：
1. 协议文档定义的是「**行首**声明格式」——`[SCOPE+]` 须在行首（列表符/引用符/粗体包裹后）。`## 8. [SCOPE+] 声明` 的标记前有**标题编号**，是**章节标题**而非声明本身；
2. 标题普遍被用作**容器**，真正的状态在其正文；实测纳入标题形态（`_SCOPE_LEAD` 追加 `(?:#{1,6}\s+)?(?:\d+\.\s*)?`，即吃掉标题编号前缀）会新增 **4 个任务转红**（`TAG0012`/`TAG0014`/`TAG0023`/`TAG0025`），需逐个人工区分「真检测」与「把容器标题当声明」；
   > **口径提示**：若把判据放宽成「**标题行内任意位置**」则可命中 6 个（多出 `TAG0004`/`TAG0008`），但那与 §3 表格中「行中出现判为提及」的口径**冲突**（同一口径在正文上会命中 24 个）——故本文件统一采用**行首**口径，数字取 **4**。
3. **代价已知且有未覆盖的真声明**：`TAG0004` 的声明本次仍不被检出（其 `P7-consistency.md:42-48` 有「### 2.1 … [SCOPE+]」节并已闭环判定）。**这是明确的既存漏检，不是遗漏申报**——本次不处理，因为处理它需要先解决「容器标题 vs 声明标题」的**语义区分**（判断类问题，不宜机械化）。
   > **⚠️ 更正**：初版把 **`TAG0008` 也列为「真声明」——不成立**（独立评审指出，我已实测确认）。`TAG0008/P2-design.md:202` 的标题 `### 4.8 设计中新发现的隐含需求（[SCOPE+] 标注意见）` 下正文首句是「**无**。调研结论 + P1 基线已覆盖全部实现决策点」⇒ 它是**容器标题 + 否定正文**，与上表第 1/2 行同类，不是真声明。把它同时归入「容器标题（会假红）」与「真声明（漏检有代价）」是**自相矛盾**。

### 3.2 已知边界二：**行首反引号**形态不覆盖，且存在真声明反例

**⚠️ 更正（独立评审指出，我已实测确认）**：初版本文与 CHANGELOG 称该写法「**一律**是引述/确定性否定」——**该表述不成立**。

实测行首反引号 `` - `[SCOPE+]` `` 的全部站点：

| 任务/文件 | 内容 | 性质 |

**决策：仍不纳入**，但理由是**可量化的取舍**而非「一律是否定」：

> **更正一处错位证据（二次更正）**：初版曾用 `TAG0025` 论证「行首反引号形态」；第一次更正写它「**不是行首**」——
> **该位置性断言不成立**（独立评审以 `od -c` 证伪，我已复核）：`TAG0025/P4-implementation.md:80` 的**第 0 字节就是反引号**

> ⇒ 这反而是**支持现行保守边界**的论据：**形态判据无法区分「折行导致的视觉行首」与真正的行首声明**。

## 8. 过程中我自己犯的一个错（如实登记）

**回写 roadmap `RM-AG0077⑦` 时，我把放宽后的正则原文（含 `(?:**|__)` 的**字面竖线**）直接粘进了表格单元格**
⇒ `roadmap.md` 该行由 9 列变 **10 列**。而**这正是本次修复所针对的同一缺陷族**：
`check-gate.py::_check_roadmap_done` 对列数 ≠ 9 的行整行跳过（RM-AG0077⑥），
而「无匹配行 → 不误拦」⇒ **`done` 反查会静默失效**。

- **发现方式**：回写后复核列数（`len(line.split("|"))`）——不是自动抓到的，是我的自检步骤抓到的。
- **修复**：按 `check-gate.py` 自身的提示改用 `&#124;` 转义（该提示正是 RM-AG0077⑥ 加的）。
- **修复后复核**：全 roadmap 列数异常行 **0**；`_check_roadmap_done("TAG0039", …)` 正常返回。
- **教训**：**在「修复某缺陷族」的同一次改动里，很容易亲手复现该缺陷族**——尤其当修复内容本身含该族的触发字符。
  这类错误靠"记得"不可靠，靠**改完立刻用同一判据复核自己改的东西**才可靠。

> 注：本文件与 CHANGELOG 中的正则展示**不受影响**（markdown 表格外的代码块/行内代码里竖线无需转义）；
> 只有**表格单元格内**需要 `&#124;`。
