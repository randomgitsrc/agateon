## 3. 我们认为最值得你质疑的四处判断

**这几处不是"已完成"的陈述，是"我们做了取舍、请你判断对不对"的地方。**

### 3.1 X2 只改一个调用点（另一处故意不改）

`pre-commit-gate.py` 有两处读 phase：

- **2d 段**：遍历的是**已暂存**的 `.state.yaml` 清单 ⇒ 「暂存区没有该文件」**不可能发生** ⇒ 直接读索引，**无需回退**；
- **2f 段**：检查「你暂存了产出但阶段不匹配」⇒ `task_state` **常常未暂存** ⇒ **不能**套用"暂存优先"语义（否则会把"未暂存"误当成"索引里的旧 phase"）。

**我（实现者）曾在两处都加回退 + 警告，触发 7 个测试回归**，随后按设计重做为单点。
**请质疑**：这个"两处语义不同"的判断是否成立？

### 3.2 X3 **保留 exit 0**，只让"未生效"可见

该 job 是 **required check**，而 GitHub 分支保护对 **skipped 的 required check 会永久阻断合并**（本仓有 PR #193 的实证）。故**不能**改成失败。

我们按「**手段②让错误可见**」处理（而非「手段①让错误不可能」——CI 机制决定了它必须 success）。
另外**已把它移出 required checks**（6 → 5）：一个**永远不会失败**的必过检查是**假保障**。

**请质疑**：移出 required 是否削弱了兜底？（其真实兜底对象是**使用者的项目侧 gate**，而本仓任务状态在 `agate-workspace/`，本仓的兜底另有其物。）

### 3.3 X4 的关键词兜底**收窄到极窄**——这是**偏离设计**的

**设计原意**：改成结构化字段为准，关键词只放"精确的肯定写法"、删掉描述性字面（如 `reuse_allowed`）作迁移期兜底。

**实现时实测：即便"精确的肯定写法"仍会误报 3 例**：

| 任务 | 原文 | 性质 |
|---|---|---|
| TAG0033 | `### 2.6 P5 证据复用判定`（**节标题**）+ 正文「本任务**不走**「复用 P5 证据」口径」 | 标题命中 + **否定式** |
| TAG0019 | 「引用 P5 证据说明：…**未在本报告作"复用"声明**」 | **否定式** |
| TAG0018 | 「…P5 证据复用**判定均通过**」 | 描述**审计跑了**，非复用声明 |

**误报为何有害**：该判据的消费方对误报不宽容——误报 ⇒ 又碰上"P5 之后改过代码"就判 `reuse_blocked` ⇒ **把根本没复用的任务拦下**。

**⇒ 实现改为只认「粗体独立声明」这一种高置信形态**（实测：命中 2 个 = 恰好 2 个真声明、0 误报；
而**旧正则命中真声明 0 个**——5 个相关文件里的真声明**全是倒序写法**）。

**代价（据实登记）**：会漏掉 `- P5 证据复用：…`（无粗体）这类朴素写法。
**独立评审意见（我们采纳）**：这是**正确的取舍**——因为漏判现在**朝安全方向失败**
（漏 ⇒ 视为"未声明" ⇒ 任务自己多跑一次回归），而误报会硬拦下从未声明复用的任务；
且**召回的正解是结构化字段**，该字段已落地。

**请质疑**：这个取舍对吗？"粗体独立声明"作为唯一兜底形态是否过于依赖写作习惯？

### 3.4 X7 改了**两个既有守护测试**的断言（2 → 1）

那两个测试把「P4 缺 `agent` ⇒ exit 2」**当作基线固定**。我们判它是**移植期快照而非 P4 应有语义**，证据是时间线：

⇒ `return 2` **早于**它被赋予"按 phase 而变"的语义约 3 周，**并非为 P4 设计**。
**独立评审复核后裁定：「改测试，不要回退代码」**（对代码事实"very high"信心）。

## 6. ⚠️ 悬置且**无归属**的问题（**最需要你判断的一项**）

### 6.1 现象：发布顺序被 CI 逼成唯一一条路

本仓的 `consistency` 是**一个 required check**，而它同时承载两类**满足时点不同**的判据：

| CHECK | 需要什么 | 在发布流程中的满足点 |
|---|---|---|
| **CHECK 7**（README badge ↔ 最新 git tag） | **tag 已存在** | **tag 之后** |
| **CHECK 13**（CHANGELOG 最新版本 ↔ UPGRADING 章节） | bump **已提交** | bump **之后即刻** |

⇒ 放同一单元 ⇒ release PR 上**必须先有 tag** ⇒ 逼出「**先推 tag，再合 PR**」。

**本次发版实测**：先推 tag 后，"badge 已改、tag 未打"引发的 **5 个测试失败**（本地与 CI 一致）
在 tag 推上去后**全部消失**——根因单一，已证实。

### 6.2 这条路**能走通**，但有已知弱点

`CHECK 7` **只看 tag 的名字**，不校验它指向哪个提交、是否为 HEAD 祖先、是否与 bump 提交一致。
**独立评审实测：把 tag 指到 `HEAD~5`（与 bump 提交无关），CHECK 7 照样 PASS。**
⇒ 若 tag 打错位置、或 PR 被否决留下**悬空 tag**，**没有任何机械判据会发现**。

### 6.3 已评估的四个方案，**每一个都有实质副作用**

| 方案 | 能否走通 | 副作用 |
|---|---|---|
| A 把 `agate/UPGRADING.md` 加入 docs-only 白名单 | ✅ | ❌ **静默关掉 CHECK 13**——而 release PR 恰是它唯一有意义的触发场合（该文件的设立缘由就是"连续两次发布漏写 UPGRADING 章节"） |
| B 豁免 `consistency` required | ✅ | ❌ 靠人记得 ⇒ 属"要求型规则"，与 ADR-015 相悖 |
| C **先推 tag**（本次采用） | ✅ | ⚠️ tag 短暂指向**未进 main** 的提交；且 tag 打错位置**无判据可察** |
| D 拆成两个 PR（UPGRADING 一个、release 一个） | ⚠️ | ❌ 把 CHECK 13 的**校验时机打散**（与 A 同类问题） |

### 6.4 根因与候选根治方案

**根因不在流程，在**：`consistency` 这个**单一 required 单元**把「需要 tag 的 CHECK 7」与
「需要 bump 的 CHECK 13」绑在了一起。

**候选根治（未落地）**：把 **CHECK 7 从 `consistency` 拆到 `release` workflow**
（后者本就以 tag push 为唯一触发器）⇒ release PR 上不再需要 tag ⇒「先 PR 后 tag」自然走通，
且 CHECK 13 在 release PR 上**照常真跑**。
**代价**：涉及 **CI 配置 + 分支保护**（required checks 变更），影响所有 PR。

### 6.5 归属现状：**它不在任何地方**

- **TAG0042 不负责它**——我 grep 了整个 P0-brief：与 consistency 相关的只有
