## 4. 本文诚实性核验

### 4.1 自述更正（"嵌套括号 17 行 → 0"）—— **不属实**

本文 §4-A 称：

> 我在交接文件中称"嵌套括号影响 **17 行真的文件存在**"。复核后**不成立**……

**核验方法** `[已实测]`：
```
git log --all --format=%H -- docs/reviews/handoff-2026-10-03-gate-robustness.md
  → 仅 2259ade 一个提交（该文件与其所在目录同批引入）
git show 2259ade:<handoff> | grep -n "17"
  → 唯一命中: 87: 若全算引用 ⇒ **517 行多出引用、701 次解析不到**  （与嵌套无关）
git log --all -p -- docs/reviews/ docs/design-notes/ | grep "17 行"
  → 命中中唯一与"嵌套括号"相关的一条，出处是
     f2baf9c:docs/reviews/handoff/design-decision-evidence-extraction.md:75  ← 本文自己
```

**结论**：**"17 行"这一声称从未出现在交接文件（任何版本）中**；在整个 git 历史里，
它与"嵌套括号"的唯一关联**就是本文自己第 75 行的这句自述**。
交接文件对嵌套括号的**实际**表述是 §3.5 的一句教训：

> `散文路径 → 收窄到括号内 → 嵌套括号 → 允许一层内层括号 → …`（第 204 行）

——这是**形态枚举序列**中的一环，**没有**附带"17 行真的文件存在"这类计数声称。

⇒ 所谓"更正先前对评审的错误说法"，**更正对象不存在**。这是**自述失实**。
`[推断]` 最可能的来源是作者把"我自己曾写过一个 17 的中间数（未落盘）"记成了"写进交接文件"，
但这属推测，本文未提供任何可复核的指向。

## 5. 新发现

### A. 归类错误：#6 `evid_ext_5_version_parens` **不属于 A/B/C 任何一类**

本文 §3 把 9 个用例按 A（#1–#5）、B（#7–#8）、C（#9）分三类，**#6 被单列为"待查"**——
但 §5 的三个问题（Q1/Q2/Q3）里**没有任何一个把 #6 纳入裁定范围**。**#6 事实上被漏掉了。**

**实测该用例的真实语义** `[已实测]`（`agate/tests/unit/test_check_p6_evidence.py:218`）：
```python
_write_p6(td, "---\nagent: test\n---\n- PASS BDD-1: upgraded (v2.0)\n")
(ev / "result.json").write_text("some evidence\n")      # ← 证据存在，只是不在括号里
result = _run_evidence(...); assert result.returncode == 0
```
以及 `extract_evidence_refs('- PASS BDD-1: upgraded (v2.0)')` → **`[]`** `[已实测]`。

⇒ 该用例断言的是「**PASS 行括号里是版本号、真证据在别处时，应 exit 0**」。
这**不是** A（嵌套括号）、不是 B（空格）、不是 C（末组 vs 全部纯路径组）——
它是**第 4 个决策**：**"PASS 行取不到引用"时该判 exit 1 还是放行**。

这与本文 §2 规则第 1–5 步**直接相关**：新规则下 `[]` 会产生"缺文件证据引用"拦截，
而该用例要求放行。**逐条实测**：9 个用例中 #6 是**唯一**属于"规则取不到引用"语义的，
它与 #1–#5、#7–#9 的失败机理**不同**（后者是"该取到的没取到"，#6 是"本就不该取到"）。

**⇒ 本文漏了第 4 个决策，且它是 9 个用例里唯一无法靠 A/B/C 裁定消解的。**

### B. 第 4 个决策（任务提示所指）：**统一提取规则对三处消费方是否都合适**

**实测事实** `[已实测]`：

| 消费方 | 实际用的提取规则 | 用途 |
|---|---|---|
| `check-p6-evidence.py:169` | `extract_evidence_refs` | 判"**有没有**"引用 |
| `check-p6-provenance.py:305` | `extract_evidence_refs` | **逐个查存在性** |
| `check-judge-verdict.py:548` | **自带** `_REF_GROUP_RE`（= `PAREN_OPEN + PAREN_INNER* + PAREN_CLOSE`，**不允许内层括号**）+ `_REF_PATH_FULL_RE` | **结论行严格匹配** |

`check-judge-verdict.py:546-549` 的注释**自认**有意分叉：

> 与 `extract_evidence_refs`（任意位置、只要像文件名）**有意不同**：
> 结论行是判据正文，须严格；PASS 行/清单是叙述，须宽松。

**三条实测结论**：
1. **不是"一处消费方"而是"两套规则"**——judge 只把**括号常量**（`PAREN_OPEN/PAREN_INNER/PAREN_CLOSE`）
   单源了，**提取规则没有单源**。这正是 ADR-014 意义上的**判据分叉**（"声明单源 ≠ 已经单源"，
   与 #388 同型）。
2. **本次分叉暂未造成行为差异**：对两仓全部 `P6.5-judge-verdict.md` 逐行比对，
   **judge 规则与统一提取器结论不一致的行 = 0** `[已实测]`（`decD.py`）。
3. **但差异是结构性的**：judge 规则**不允许内层括号**，而统一提取器**允许**。
   ⇒ 一旦决策 A 选 **A2**，**judge 不会跟着放宽**，两处会立刻分叉；
   即便选 A1（推荐），这条分叉也只是"恰好无触发语料"，属**潜在判据分叉**。

**⇒ 这是本文未提出的第 4 个决策**：三处用途不同，统一提取规则**对 judge 未必合适**。
建议明确裁定：(a) judge 保持严格（须在 ADR 或 docstring 登记为**有意偏离**并加等价守护），
或 (b) judge 也改走统一提取器（须实测其对结论行的召回影响）。**本文对此完全未提。**
