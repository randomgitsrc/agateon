# Agateon 文档选材与保鲜指南

> 适用：任何在本仓库**新增 / 修改 .md 文档**的 agent 或开发者（AGENTS.md、README、导航文档、
> 指南、设计文档、复盘等）。
> 目的：让仓库里的文档**长期保鲜**——不写死会漂移的东西，只记"不读就不知道"的东西。
> 权威出处：根 `AGENTS.md` 引言区（"只收录不读就不知道的内容"）为本指南的浓缩版；本指南是完整版。
> 触发块：开始写 / 改任何 .md 之前先读本指南第 1 节选材判据。

---

## 1. 选材判据（这条内容到底该不该写进文档）

**核心判据：如果读者不知道这条，会做错什么 / 浪费多少时间？**

- 能答出**具体损失** → 记录（这是"不读就不知道"的内容）
- 答不出具体损失，或读者一条命令就能自己查到 → **不记录**

| 应该记 | 不该记 |
|--------|--------|
| 不读就不知道的**稳定规则**（gate 纪律、测试约定、发布清单、工具纪律）| 可从仓库读到的（目录结构、命令、CI 配置、协议正文）|
| **本机环境事实**（`~/.agate` 路径、venv 位置、git 脚本绝对路径）| **频繁变动的数字统计**（用例数 / commit 数 / 条目数 / HEAD 日期）|
| **历史教训**（事故 → 纪律的由来，如 T001/TAG0004）| 当前版本号写死（README badge 是例外，见 §2）|
| **指向权威源的指针**，不抄权威源正文 | 主观泛泛（"写好测试""注意质量"这类无操作性的说法）|

## 2. 数字不写死纪律

**时变数字统计一律不写进正文**，需要时用命令或权威源指针替代：

| 想表达 | 不写死，改为 |
|--------|------------|
| 现在有多少测试用例 | `bash agate/tests/scripts/count-tests.sh` |
| 当前版本 / 最新 tag | README badge、`git describe --tags` |
| 已完成多少任务 / 债条目 | `agate-workspace/tasks/active-tasks.md`、`roadmap.md`、`tech-debt.md` |
| HEAD 提交日期 | 不写（`git log -1` 可查）|

**机械门禁（2026-10-02 起）**：`check-protocol-consistency.py` **CHECK 16「活文档数字漂移」**
把上面两条**从约定升级为门禁**（此前只登记为「❌ 非机械门禁」，而约定不拦人——`tests/README.md`
的用例数列就是这样漂到 44% 的）。它检两件事：
① 活文档里的**测量声称须带时态锚**（规则见 §2.1）；② 表格**不得有计数列**。
范围 = 活文档（协议本体 + 开发指引 + 根文档）；记录类（`tasks/`、`reviews/`、`site/blog/`、`fixtures/`）
**刻意不覆盖**——它们本就是历史快照，全体带锚反而失真。

**保留的合法例外**：

- **稳定结构事实**（如"脚本三大族""9 个子目录"）——变化频率极低，可写
- **本机环境事实**（路径 / venv / 软链）——变化会被人为迁移，写死反而有提醒作用
- **有自动维护机制的值**：README version badge（CHECK 7 校验 badge↔tag，发布时同步）——是例外，可写死
- **证据类数字**——**合法，但必须带时态锚**（见下）

### 2.1 证据类数字：可写，但必须锚定"哪一刻"

"本次实测 unit 2309 passed"这类数字是**论证的必要证据**（不写就无法证明"没破坏"），
不能删。**但它与"现状描述"必须可区分**——否则读者无法判断这是"当时的实测"还是"当前的声称"，
下次代码前进后它就变成**隐性错误声称**。

| 写法 | 判定 |
|---|---|
| `unit 2309 passed` | ❌ 无时态——读者会当现状读；下次前进即失真 |
| `unit 2309 passed @ cd942ac` | ✅ 锚定 commit |
| `unit 2309 passed（实测于 2026-10-02）` | ✅ 锚定日期 |
| `unit 2309 passed（改动前实测）` | ✅ 锚定相对时点（在对比语境中成立） |

**为什么这条重要（2026-10-02 实证）**：同一批 CHANGELOG 里出现 `unit 2309 passed`
与 `count-tests 2529`，而当时实际为 `2311 / 2531`——**数字本身是当时真实测得的，
错在没标时态**，导致后续读者（含我自己）反复把它当现状核对，制造了多轮无效返工。

**实证教训（2026-08-30）**：`docs/guides/project-map.md` 写死 HEAD 日期 / commit 数 / 条目数，
3 天内因仓库前进而全部过期。修法不是"刷新数字"，而是**改成指针式**——刷新仍会再次过期。

## 3. 历史快照 vs 活文档

写数字前先判断文档性质：

| 性质 | 例子 | 数字是…… | 处理 |
|------|------|----------|------|
| **历史快照** | `archived/`、`tasks/`、`reviews/`、`site/blog/` 的产出、**CHANGELOG 已发布版本的条目** | "当时状态"的记录 | **保留不动**，改反而失真 |
| **活文档** | 根 `AGENTS.md`、`docs/guides/*`、`agate/*.md`、`agate/phase-cards/*`、`agate/scripts/README.md`、`agate/tests/README.md` | 会漂移的状态 | 只写指针，不写死 |

**判据（不是举例——凡命中即活文档，无论它在哪个目录）**：

> **文档的读者是"现在/未来的执行者"，且它会随代码/任务推进被再次编辑 → 活文档。**

反例不成立："它在 `agate/tests/` 下所以是测试资料"——`agate/tests/README.md` 就是活文档，
它曾写死 68 行逐文件用例数，**实测 30 行已漂移（44%）**，如 `check-gate.py` 声称 144、实际 203。

**⚠️ 分类靠"举例"是不够的（2026-10-02 实证）**：§3 原表把活文档举例为"根 `AGENTS.md`、
`project-map.md`、本指南"——`tests/README.md` 不在例中，于是它**从未被这条纪律覆盖**，
数字一路漂到 44%。**故本次改为判据式；新增文档时按判据自查，不要等它出现在例子里。**

## 4. 指针式原则

- 不重复权威源正文，只指路："详细内容见 `xx.md` §N"
- 新增机制 / 目录 / CI job 落地后，同步更新导航文档（如 `docs/guides/project-map.md` 第 2 / 4 / 5 节）
- 文档内部不维护权威源的副本；发现某处需要展开 → 写到对应权威源，这里留指针

## 5. 变更日志约定

- 文档的变更日志（如 `## 变更日志`）只记"**做了什么改动**"，不记会漂移的当前状态
- 快照信息（"当时是 vX / N 条 / 某日期"）如果要留，作为历史写入变更日志条目，**不进正文**
- 改动后同步：正文改了什么 → 变更日志补一条（日期 + 一句话）
