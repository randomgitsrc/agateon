## task

「治理**派发的单位成本与总量**：① 定点修订不再使整个评审面板失效（消除"改一处、重派全panel"与其带来的"故意不修已知缺陷"逆向激励）；② 为产物设定"最小充分"判据（不再出现 24 行代码配 82KB 设计）；③ 派发上下文按需供给（卡片不重复注入、纪律不在 per-task 复述、修订轮只给增量）。」

## 合并依据（为何 RM-AG0072/0073 是一个 task）

两者是**同一成本方程的两端**，且**共用同一批文件**：

| RM | 作用对象 | 共同文件 |
|---|---|---|
| RM-AG0072 | **单位派发的次数与体量**（面板重放轮数 × 每份产物体积） | `dispatch-protocol.md` / 阶段卡 / 评审角色 |
| RM-AG0073 | **单份派发上下文的供给**（卡片 60% 重复 + 纪律双载 + 修订轮全量复述） | `assets/templates/dispatch-prompt.md` / `agate-inject-card.py` / 阶段卡 |

分两批改会在同一批文件上改两遍、跑两遍一致性 → 强合并。

## 实测证据

### 证据 A：面板重放 = 每轮修订重派整个面板

TPV0099 的 P2：**4 个角色 × 2 轮 = 8 份派发上下文 / 320KB**，仅为**一轮定点修订**。机制成因：任一修订使该产出的**全部 approved 立即失效**（评审批准的是特定修订版本）→ 必须整panel重派。

### 证据 B：重放产生「故意不修已知缺陷」的逆向激励（主 Agent 自述）

TPV0099 orchestrator-log 明确记录：为省一轮评审而**故意不修**两处已知措辞缺陷——

> 「此刻再改该文件（哪怕只改措辞）会使两份 `approved` 立即失效 → 须再走一轮评审 = 额外消耗 retry 预算（P2 cap 3）…为两处措辞级非阻塞项付这个代价**不成比例**」

→ **机制在奖励"带已知缺陷发货"**，正是协议自己批判的债务制造模式。

### 证据 C：产物体量无上限

| 项 | TPV0099 实测 |
|---|---|
| 真实产品代码 | **24 行**（3 文件） |
| P2 设计 | **735 行 / 81,931 字节** |
| P2 评审（单份） | 22,304–28,753 字节 |
| 任务目录总计 | 3.5MB |

评审者必须**读完 82KB 设计**才能产出评审——token 成本由产物体量驱动，而体量**无任何约束**（无「最小充分产物」原则、无大小上限）。

### 证据 D：派发上下文 60% 是同一条卡片的重复注入（逐文件实测）

26 份派发上下文 / 678KB（字符计）：

| 文件 | 总计 | 卡片块 | **卡片占比** |
|---|---|---|---|
| `P1-dispatch-context-analyst.md` | 18,421 | 10,636 | 58% |
| `P2-dispatch-context-architect-rev1.md` | 26,863 | 14,776 | 55% |
| `P1-dispatch-context-analyst-rev2.md` | 14,576 | 10,636 | **73%** |
| `P2-dispatch-context-plan-design-review-rev1.md` | 19,362 | 14,776 | **76%** |
| … | | | |
| **合计** | **417,773** | **251,346** | **60%** |

注入是机械的 `agate-inject-card.py`，**无按需裁剪**；修订轮的卡片占比反而更高（rev2 达 73-76%）。

### 证据 E：纪律双重承载（同一约束多处维护）

`assets/templates/dispatch-prompt.md`（18,591 字节）已有「环境隔离」「命令超时兜底」「任务粒度兜底」等通用节；而 26 份 per-task 上下文中仍：

- **16 份**重申「环境与纪律」
- **15 份**重申探针落位
- **13 份**重申 flaky 清单

→ 同一约束**两处维护**，逐轮重复；模板改了 per-task 副本不会跟。

### 证据 F：修订轮几乎整篇重写

字符级重合度（剥离卡片块后）：**6%–12%**（`P2-architect` → `-rev1` 仅 **6%**，且自撰部分反而从 8,679 → 12,087 字节）。即每轮**几乎整篇重写**，而**实际新增信息量远小于篇幅**。

## scope

### 子批 A：修订不再重放整个面板（RM-AG0072 主体）

- 定义**增量评审**语义：定点修订只需重审**受影响面**（附「变更范围证据」），而非整panel
- 明确**什么情况下必须整panel重派**（如方案层变更 / 接口契约变更）与**什么情况下只需定点复审**
- 消除逆向激励：非阻塞项在「已 approved」状态下的后续处理路径须明确（不再让主 Agent 在"修了要重审"与"不修留债"之间二选一）

### 子批 B：产物「最小充分」判据（RM-AG0072）

- 为阶段产出定义**最小充分**原则与可判定判据（避免「24 行代码 → 82KB 设计」）
- 与既有 `design_trivial` / `follows_existing_pattern`（**唯一已真接线的旋钮**，`check-gate.py:865`）的关系须说明——可复用之，不另造机制
- **不得**退化为「按行数卡上限」（会鼓励注水/删必要信息）；方向是「**该写的写全、不该写的不写**」的可判定判据

### 子批 C：派发上下文按需供给（RM-AG0073）

- **卡片**：从「整块机械注入」改为**按需引用 + 决策相关摘录**（子代理本有文件读权限，可自行读卡片）
- **纪律单一来源**：`dispatch-prompt.md` / 角色文件为唯一来源，**per-task 上下文不复述**
- **修订轮**：只给**增量规格**（不整篇复述上一轮）
- 保留硬约束：dispatch-context 必须自洽（子代理无其他上下文）——**「不多不少」而非「越少越好」**

## 验收基线（倾向，P1 细化）

1. Given 一次定点修订（仅非阻塞措辞级） When 走评审 Then **重审的评审数 < 面板规模**（可数），且**不使全部既有 approved 失效**
2. Given 阶段产出 When 对照「最小充分」判据 Then 有**可二值判定**的判据（不依赖主观「够不够」），且该判据被阶段卡与评审角色引用
3. Given 26 份量级的派发上下文 When 统计 Then **卡片占比 ≤ 20%**（TPV0099 基线 60%，可脚本量测）
4. Given 同一通用约束（如环境隔离） When 全文检索 Then **只在 1 处维护**（计数 + 引用关系可查）
5. Given 修订轮派发上下文 When 检查 Then **只承载增量规格**（与上一轮的重合度不再接近全篇——可量测）
6. Given 全量 pytest + consistency When 跑 Then 全绿 / 0 ERROR

## known_risks

- **同类/影响面预判——同类实例**：面板重放**不止 P2**——P1/P4/P7 同样是「自撰产出 gate」，任一修订都使既有 approved 失效。TPV0099 实测 P1 跑了 **3 轮**评审（含 `-rev1`/`-rev2`）、P2 跑了 **2 轮双评审 + 组长**、P4 一轮复审。**本任务须处理全部走评审的阶段，不能只改 P2**。P1 同类扫描须列出所有「评审使 approved 失效」的路径。
- **同类/影响面预判——上下游消费方**：改 `dispatch-protocol.md` 的编排语义会牵动 **9 张阶段卡**（各自引用该节）、`assets/templates/dispatch-prompt.md`、`assets/templates/dispatch-context.md`、各评审角色文件、`agate-inject-card.py`、`agate-render-dispatch-prompt.py`、`agate-dispatch.py`，以及 `check-structure-consistency.py` 的 **S-1/S-2 双向一致性**（YAML↔md 锚点）。改卡片注入形态还会牵动 `check-p6-provenance.py` 的**审计 2**（dispatch-context 内容约束——TPV0099 曾因格式样例落在 CARD 块外被 exit 1 拦）。
- **🔴 最大风险：上下文「瘦身」过头 = 让子代理缺必要信息**，会产生比现状更贵的结果（白跑一轮 / 产出错的东西）。**「不多不少」的判据必须可验证**（子代理能否仅凭上下文 + 文件读权限完成任务），不能只看体积下降。**TPV0099 的 26 份上下文里，主 Agent 反复重申的纪律恰恰是因为踩过坑才写的**——删之前必须证明「模板/角色文件已覆盖该约束」。
- **🔴 第二个高风险：改评审失效语义会削弱独立复核的价值**。TPV0099 的评审**确实抓到真缺陷**（P1 8 条必修含判据必 FAIL；P2 抓到「按设计实现会打红两个既有 gate 键」；P4 抓到清理钩子假绿）。**「减少重放」不得变成「减少评审」**——判据必须保证：**方案层/接口层变更仍重审，仅非实质变更可定点复审**。
- **审计 2 的耦合**：`agate-inject-card.py` 注入形态若改变（如改为引用），`check-p6-provenance.py` 的审计 2（扫描 dispatch-context 是否含行首 PASS/FAIL 预判）的**扫描面会随之变化**——须与 **TAG0039**（`check-p6-provenance.py` 修复）协调，避免两边同时改同一脚本。**建议：本任务若需改该脚本，先与 TAG0039 的主 Agent 确认顺序**（或本任务不改它，只改被它扫描的产物形态）。
- **本仓已有相关 `done` 条目的边界（防误读为重复）**：RM-AG0016（派发编排机制）交付的是**派发数量与拆分**侧（工作量评估五维 + 五模式 + 并行上限 3）；RM-AG0026（测试重跑审计与跨阶段证据引用）交付的是**gate 命令证据复用**（`--audit7-only`）。本条治理的是**单份上下文的信息供给**与**评审失效范围**，与之互补不重叠。
